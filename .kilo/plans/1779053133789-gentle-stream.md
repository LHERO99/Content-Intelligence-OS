# Plan: Fix Content-Erstellung Display Issues

## Problems Summary

Nach der Implementierung des Execution-Cycle-Fixes gibt es zwei verbleibende Probleme:

### Problem 1: Auftragsliste zeigt nicht nur Main Keywords
**Symptom**: In der Content-Erstellung Auftragsliste werden ALLE Keywords angezeigt, nicht nur Main Keywords.

**Root Cause**: Der Filter in `/src/app/creation/page.tsx` (Zeile 65-82) prüft nur den Status, nicht ob es ein Main Keyword ist.

### Problem 2: "KI generiert gerade den Content" trotz vorhandenem Content
**Symptom**: Obwohl Content bereits erstellt wurde, wird noch "KI generiert gerade den Content" angezeigt.

**Root Cause**: Der Content wird nicht in `execution_versions` Tabelle gespeichert, wenn Content angeliefert wird.

## Root Cause Analysis

### Problem 1: Missing Main Keyword Filter

**Aktueller Code** (`creation/page.tsx:65-82`):

**Problem**: Kein Check für `keyword.Main_Keyword === 'Y'`

**Konsequenz**: Nicht-Haupt-Keywords werden auch in der Auftragsliste angezeigt, obwohl sie denselben Execution Cycle wie das Haupt-Keyword teilen.

### Problem 2: Content Storage Architecture

**Neue Schema-Architektur** (3-Tabellen-System):
1. **execution_cycles** - Tracks workflow status (commissioned, in_progress, delivered)
2. **execution_versions** - Stores actual content HTML + metadata
3. **process_events** - Event log with references to cycle and version

**Content Flow sollte sein**:
1. Commission → Create execution_cycle (status='commissioned')
2. Delivery → Create execution_version + Update cycle (status='delivered') + Create process_event

### Fix 2: Create execution_version When Saving Content

#### Step 2.1: Create Helper Function in postgres.ts

**File**: `/src/lib/postgres.ts`
**Location**: After `createExecutionCycle()` (around line 636)

```typescript
/**
 * Creates a content version in the execution_versions table.
 * Returns the version ID.
 */
export async function createExecutionVersion(
  cycleId: number,
  contentHtml: string,
  options?: {
    diffSummary?: string;
    createdByUserId?: string;
    createdByAi?: boolean;
    aiProvider?: string;
    aiModel?: string;
    aiInstructions?: string;
  },
  tenantId?: string
): Promise<number> {
  const tenant = tid(tenantId);
  return withTenant(tenant, async (tx) => {
    // Get next version number for this cycle
    const [result] = await tx
      .select({ 
        maxVersion: sql<number>`COALESCE(MAX(${executionVersions.versionNumber}), 0)` 
      })
      .from(executionVersions)
      .where(
        and(
          eq(executionVersions.cycleId, cycleId),
          eq(executionVersions.tenantId, tenant)
        )
      );
    
    const nextVersionNumber = (result?.maxVersion ?? 0) + 1;
    
    // Create new version
    const [version] = await tx
      .insert(executionVersions)
      .values({
        tenantId: tenant,
        cycleId,
        versionNumber: nextVersionNumber,
        contentHtml,
        diffSummary: options?.diffSummary,
        createdByUserId: options?.createdByUserId || null,
        createdByAi: options?.createdByAi ?? true,
        aiProvider: options?.aiProvider,
        aiModel: options?.aiModel,
        aiInstructions: options?.aiInstructions,
      })
      .returning({ id: executionVersions.id });
    
    return version.id;
  });
}
```

## Risks & Mitigation

**Risk**: Breaking existing content display  
**Mitigation**: New Version_Id parameter is optional, backward compatible

**Risk**: Version creation fails  
**Mitigation**: Wrap in try-catch, log errors but continue

**Risk**: Legacy data without versions  
**Mitigation**: getContentLogs() already handles NULL versions (returns v1)

## Notes

- The execution_versions table is the ONLY place where content HTML is stored
- process_events is just an event log - it references versions but doesn't store content
- Content_Body in createContentLog was always ignored - this wasn't a regression
- The new architecture separates concerns: cycles=workflow, versions=content, events=audit

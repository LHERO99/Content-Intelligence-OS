# Plan: Fix Content Workflow - Schema Architecture Issues

## Current Status: Implementation Failed ⚠️

### New Problems After First Implementation
1. **Problem A**: When adding ONE keyword to Redaktionsplan, ALL keywords of that URL appear in Redaktionsplan
2. **Problem B**: Commissioned content no longer appears in Content-Erstellung Auftragsliste

## Root Cause Analysis

### The Fundamental Architecture Mismatch

The system has TWO schemas with incompatible designs:

**Old Schema (Expected by Frontend)**:
- `Keyword_Map` table: Each keyword is independent
- Each keyword has its OWN status (`Planned`, `Beauftragt`, etc.)
- Users can add individual keywords to planning workflow

**New Schema (Current Backend)**:
- `urls` + `planning_status`: Status is per URL, NOT per keyword
- `planning_status.urlId` → One status for ALL keywords of a URL
- When main keyword → `Planned`, ALL keywords of that URL inherit `Planned`

### Why This Causes Problems

#### Problem A: All Keywords Appear in Redaktionsplan

**Flow:**
1. User clicks "Hinzufügen" for Keyword A (Main_Keyword = 'Y')
2. Backend calls `updateKeyword(keywordA_id, { Status: 'Planned' })`
3. Backend updates `planning_status` WHERE `urlId = keywordA.urlId`
4. ALL keywords of that URL now return `Status = 'Planned'` via `mapToOldStatus()`
5. Frontend filters: `keywords.filter(k => k.Status === 'Planned')`
6. Result: ALL keywords of URL appear in Redaktionsplan, not just Keyword A

**Code locations:**
- `/src/lib/postgres.ts:478-506` - Updates planning_status by urlId
- `/src/lib/postgres.ts:96-122` - mapToOldStatus() returns status for all keywords
- `/src/app/planning/editorial-planning.tsx:76` - Filters by Status === 'Planned'

#### Problem B: Commissioned Content Not Visible

**Flow:**
1. First implementation added logic: Non-main keywords (`isMainKeyword = false`) return `'Backlog'` during planning
2. This prevents them from showing `Status = 'Planned'` in Redaktionsplan (intended)
3. BUT: It also prevents them from showing `Status = 'Beauftragt'` in Content-Erstellung (unintended!)
4. The filter at `/src/app/creation/page.tsx:64-81` requires `keyword.Status === 'Beauftragt'`
5. Result: Commissioned keywords with `isMainKeyword = false` are filtered out

**Code location:**
- `/src/lib/postgres.ts:104-111` - Non-main keywords stay in 'Backlog' (too restrictive)

## Possible Solutions

### Option 1: Filter Redaktionsplan to Show Only Main Keywords ✅ (Recommended)

**Concept**: Accept that status is per-URL in new schema, but filter frontend to show only main keywords in planning views.

**Changes needed:**
1. **Revert** the `mapToOldStatus()` changes (restore original behavior)
2. **Update** Redaktionsplan filter to show only `Main_Keyword === 'Y'` AND `Status === 'Planned'`
3. **Keep** the Content-Erstellung filter improvements (status verification)

**Pros:**
- Minimal changes
- Works with existing schema
- Maintains frontend expectations
- All keywords share URL-level status (architecturally correct for new schema)

**Cons:**
- Cannot plan non-main keywords individually
- User can only add main keywords to planning workflow

**Implementation:**
```typescript
// editorial-planning.tsx:76
const plannedKeywords = React.useMemo(() => {
  return keywords.filter(k => 
    k.Status === 'Planned' && 
    k.Main_Keyword === 'Y'  // Only show main keywords in planning view
  );
}, [keywords]);
```

### Option 2: Add Per-Keyword Status Table ⚠️ (Complex)

**Concept**: Create new table `keyword_planning_status` to track status per keyword, not per URL.

**Changes needed:**
1. Create new migration: `keyword_planning_status` table with `keywordId` FK
2. Update `updateKeyword()` to write to new table
3. Update `getKeywordMap()` to read from new table
4. Migrate existing data from `planning_status` to `keyword_planning_status`

**Pros:**
- Each keyword can have independent status
- Architecturally clean
- Supports full requirements

**Cons:**
- Major schema change
- Data migration required
- Significant testing needed
- May break other parts of system

### Option 3: Use Keyword-ID Tracking in planning_status ⚠️ (Hybrid)

**Concept**: Add `mainKeywordId` field to `planning_status` to track which specific keyword was planned.

**Changes needed:**
1. Add `mainKeywordId` column to `planning_status`
2. Update queries to join by both `urlId` AND `mainKeywordId`
3. Filter logic to match keyword ID

**Pros:**
- Preserves URL-centric design
- Allows tracking which keyword was planned

**Cons:**
- Still doesn't solve independent keyword planning
- Confusing hybrid model

## Recommended Solution: Option 1

**Reasoning:**
- Fastest to implement
- Least risk
- Aligns with new schema's URL-centric design
- Users primarily work with main keywords anyway

**Trade-off:**
- Users can only add main keywords to planning workflow
- Non-main keywords automatically follow main keyword's status
- This is acceptable: planning workflow is for URLs/pages, not individual keywords

## Implementation Plan (Option 1)

### Step 1: Revert mapToOldStatus Changes

**File**: `/src/lib/postgres.ts`

Revert to original:
```typescript
function mapToOldStatus(
  planning: typeof planningStatus.$inferSelect | null,
  execution: typeof executionCycles.$inferSelect | null,
  publishing: typeof publishingStatus.$inferSelect | null
): KeywordStatus {
  // All keywords inherit URL-level status
  if (publishing?.status === 'published') return 'Published';
  if (publishing?.status === 'in_review') return 'Review';
  if (execution?.status === 'delivered') return 'Angeliefert';
  if (execution?.status === 'in_progress') return 'In Arbeit';
  if (execution?.status === 'commissioned') return 'Beauftragt';
  if (planning?.status === 'planned') return 'Planned';
  return 'Backlog';
}
```

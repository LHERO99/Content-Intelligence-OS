# Plan: Fix Content Workflow - Prevent Pre-Commission Display in Auftragsliste

## Problem Analysis

### Current Behavior (Bug)
1. User clicks "Hinzufügen" in Tab "Vorschläge" → Status changes to `"Planned"`
2. The topic appears correctly in Tab "Redaktionsplanung"
3. **BUG**: The topic already appears in the "Auftragsliste" (assignment list) of Content-Erstellung, even though it has NOT been commissioned yet
4. User clicks "Beauftragen" in Redaktionsplanung → Workflow should trigger and commission the content

### Expected Behavior
1. User clicks "Hinzufügen" in Tab "Vorschläge" → Status changes to `"Planned"`
2. The topic appears in Tab "Redaktionsplanung"
3. **The topic should NOT appear in Content-Erstellung yet**
4. User clicks "Beauftragen" in Redaktionsplanung → Status changes to `"Beauftragt"`, commission log is created, N8N workflow triggers
5. **Only NOW** should the topic appear in the "Auftragsliste" of Content-Erstellung

### Root Cause
The Auftragsliste in `/src/app/creation/page.tsx` (lines 64-66) builds the job list from content logs with:
```typescript
const commissioningLogs = contentLogs.filter(
  (l) => l.Event_Label === 'Content wurde beauftragt',
);
```

However, somewhere in the codebase, a "Content wurde beauftragt" log entry is being created **prematurely** when a topic is added to the editorial planning (Status → "Planned"), instead of only when it's actually commissioned (Status → "Beauftragt").

**The current codebase correctly prevents premature commission logs.** The commission log creation logic only triggers when:
- Status is explicitly set to `"Beauftragt"`
- The "Beauftragen" button is clicked
- The N8N trigger endpoint is called with COMMISSION actions

### Possible Root Causes

Since the code is correct, the issue must be one of these:

1. **Data layer confusion**: The system uses TWO schemas:
   - Old schema: `Keyword_Map` table with `Content_Log` entries
   - New schema: `urls`, `execution_cycles`, `process_events` tables
   - The `/api/planning/history` endpoint queries the NEW schema (`process_events`)
   - The planning components still use the OLD schema (`Keyword_Map`, `Content_Log`)

2. **Event mapping issue**: Line 967 in `/src/lib/postgres.ts`:
   ```typescript
   Event_Label: (event.eventData as any)?.original_event_label || event.eventType,
   ```
   - This maps new schema events to old schema event labels
   - Could be mapping `url_planned` → `"Content wurde beauftragt"` incorrectly

3. **Pre-existing data**: Old commission logs from before bugfixes

4. **Incorrect Status filter**: The issue might be in how keywords are filtered, not in log creation

## Proposed Solution

### Root Cause Confirmed: Event Type Mapping Issue ✅

**Found the bug!** In `/src/lib/postgres.ts` at lines 604 and 967:

```typescript
Event_Label: (event.eventData as any)?.original_event_label || event.eventType,
```

**The Problem:**
- When `original_event_label` is not set, it falls back to raw `event.eventType` enum values
- `event.eventType` contains values like: `'url_planned'`, `'cycle_commissioned'`, `'url_suggested'`, etc.
- These raw enum values are NOT being translated to German event labels
- The frontend expects specific German labels like `'Content wurde beauftragt'`
- **However**, there might be a data inconsistency where some events have the wrong `eventType` or missing proper labels

**Why this causes the bug:**
- If `url_planned` events somehow have `eventType = 'cycle_commissioned'`, they would show as commission logs
- OR if the event mapping logic (lines 658-664 in `createContentLog`) is assigning wrong event types when status changes to "Planned"

### Solution Steps

#### Step 1: Add Proper Event Type Mapping Function
**File**: `/src/lib/postgres.ts`

Add a mapping function to correctly translate event types to German labels:

```typescript
/**
 * Maps new schema event types (process_events.event_type) to old schema German event labels.
 * This ensures backward compatibility with components expecting German event labels.
 */
function mapEventTypeToLabel(eventType: string): string {
  const mapping: Record<string, string> = {
    // Planning phase
    'url_suggested': 'URL wurde dem Tab \'Vorschläge\' hinzugefügt',
    'url_added_to_backlog': 'URL wurde dem Tool hinzugefügt',
    'url_planned': 'URL wurde der Redaktionsplanung hinzugefügt',
    'planning_cancelled': 'Planung abgebrochen',
    
    // Execution phase
    'cycle_commissioned': 'Content wurde beauftragt',
    'cycle_started': 'Content-Erstellung gestartet',
    'cycle_delivered': 'Content angeliefert',
    'cycle_failed': 'Content-Erstellung fehlgeschlagen',
    
    // Content version phase
    'version_created': 'Version erstellt',
    'version_edited': 'Inhalt bearbeitet',
    
    // Publishing phase
    'submitted_for_review': 'Zur Review eingereicht',
    'review_approved': 'Review genehmigt',
    'review_rejected': 'Review abgelehnt',
    'content_published': 'Content veröffentlicht',
    'content_unpublished': 'Content offline genommen',
    
    // Blacklist
    'url_blacklisted': 'URL auf Blacklist gesetzt',
    'url_unblacklisted': 'URL von Blacklist entfernt',
    
    // Keywords
    'keyword_added': 'Keyword hinzugefügt',
    'keyword_removed': 'Keyword entfernt',
  };
  
  return mapping[eventType] || eventType;
}
```

Then update lines 604 and 967 to use this mapping:

```typescript
// Line 604 (in getContentLogs)
Event_Label: (event.eventData as any)?.original_event_label || mapEventTypeToLabel(event.eventType),

// Line 967 (in getContentHistoryByUrl)
Event_Label: (event.eventData as any)?.original_event_label || mapEventTypeToLabel(event.eventType),
```

**Also check line 631** (in `getContentLogBody`):
```typescript

```

#### Step 2: Add Status Safeguard in Frontend (Defense in Depth)
**File**: `/src/app/creation/page.tsx`
- Lines 64-66: The commission log filter

**Add additional safeguard** to double-check keyword status:
```typescript
const commissioningLogs = contentLogs.filter((l) => {
  const keywordId = l.Keyword_ID?.[0];
  if (!keywordId) return false;
  
  // Must have the correct event label
  if (l.Event_Label !== 'Content wurde beauftragt') return false;
  
  // Extra safety: keyword must actually be in "Beauftragt" status
  const keyword = kwMap[keywordId];
  if (!keyword) return false;
  
  // Only show if keyword is actually commissioned (not just "Planned")
  return keyword.Status === 'Beauftragt' || 
         keyword.Status === 'In Arbeit' || 
         keyword.Status === 'Angeliefert' || 
         keyword.Status === 'Review' ||
         keyword.Status === 'Published';
});
```

This provides defense-in-depth: even if the event mapping is incorrect, we verify the actual keyword status before showing it in the Auftragsliste.

**This looks correct**, but we should verify it's assigning proper event types. Consider adding more specific mappings:

```typescript
function mapLabelToEventType(eventLabel?: string): string {
  if (!eventLabel) return 'version_created';
  
  // Commission events
  if (eventLabel === 'Content wurde beauftragt') return 'cycle_commissioned';
  
  // Delivery events
  if (eventLabel === 'Content angeliefert') return 'cycle_delivered';
  
  // Planning events
  if (eventLabel === 'URL wurde der Redaktionsplanung hinzugefügt') return 'url_planned';
  if (eventLabel === 'URL wurde dem Tab \'Vorschläge\' hinzugefügt') return 'url_suggested';
  if (eventLabel === 'URL wurde dem Tool hinzugefügt') return 'url_added_to_backlog';
  
  // Publishing events
  if (eventLabel === 'Content veröffentlicht') return 'content_published';
  
  // Default
  return 'version_created';
}
```

This ensures exact matching and prevents any ambiguity with `.includes()` checks.

## Summary

### The Bug
When users click "Hinzufügen" (Add) in the Vorschläge tab, topics correctly move to Redaktionsplanung with `Status = "Planned"`. However, they also **incorrectly** appear immediately in the Content-Erstellung Auftragsliste, even though they haven't been commissioned yet.

### The Root Cause
The system uses dual database schemas:
- **Old schema**: `Keyword_Map` table with German event labels in `Content_Log`
- **New schema**: `process_events` table with English event type enums

The API endpoint `/api/planning/history` queries the new schema but maps events to the old format. The mapping function at lines 604, 631, and 967 in `postgres.ts` falls back to raw `event.eventType` values when `original_event_label` is missing:

```typescript
Event_Label: (event.eventData as any)?.original_event_label || event.eventType
```

This means `event.eventType` values like `'url_planned'` or `'cycle_commissioned'` are returned as-is instead of being translated to German labels like `"URL wurde der Redaktionsplanung hinzugefügt"` or `"Content wurde beauftragt"`.

If there's any data inconsistency or event type mismapping, planned items could incorrectly show commission event types, causing them to appear in the Auftragsliste prematurely.

### The Solution
**Two-part fix:**

1. **Event Type Translation** (Core Fix):
   - Add `mapEventTypeToLabel()` function to properly translate English event types to German labels
   - Update all event label mappings to use this function
   - Ensures `'url_planned'` → `"URL wurde der Redaktionsplanung hinzugefügt"` (not commission event)
   - Ensures `'cycle_commissioned'` → `"Content wurde beauftragt"` (only this should appear in Auftragsliste)

2. **Status Verification** (Safety Net):
   - Add keyword status check when filtering commission logs in `creation/page.tsx`
   - Even if event labels are incorrect, only show items with actual commissioned status
   - Defense-in-depth approach

### Why This Will Work
- Fixes the event type → label translation at the data layer
- Adds frontend validation as a safeguard
- Maintains backward compatibility with old schema components
- No changes needed to existing commission/planning workflows

## Notes

- The codebase uses dual schemas: old (`Keyword_Map`, `Content_Log`) and new (`urls`, `planning_status`, `execution_cycles`, `process_events`)
- The bug occurs in the schema bridging layer where new events are mapped to old format
- This fix improves the schema migration compatibility
- All commission and planning workflows remain unchanged
- The fix is minimal, focused, and low-risk

# Plan: User-Anzeige in Content-Historie hinzufügen

## Ziel
Bei jedem Event in der Content-Historie soll angezeigt werden, welcher User die Aktion ausgeführt hat (Name und/oder E-Mail).

## Aktueller Stand

### ✅ Was bereits funktioniert
- **User-Tracking wird bereits erfasst**: Die `process_events` Tabelle hat ein `user_id` Feld
- **User-IDs werden gespeichert**: Bei den meisten Events wird `session.user.id` erfasst und in der Datenbank gespeichert
- **User-Daten sind verfügbar**: Die `users` Tabelle enthält alle User-Informationen (id, name, email, role)

### ❌ Was fehlt
- **Keine Anzeige der User-Namen**: Die aktuelle `getContentLogs()` Funktion holt nur die User-IDs, nicht die Namen
- **Kein JOIN mit users Tabelle**: Die Datenbankabfrage verbindet `process_events` nicht mit `users`
- **UI zeigt keine User-Information**: Die Frontend-Komponenten zeigen derzeit keine User-Information an

## Implementierungsplan

### 1. Backend: Datenbankabfrage erweitern

**Datei**: `/src/lib/postgres.ts`  
**Funktion**: `getContentLogs()` (circa Zeile 866-907)

**Änderungen**:
- LEFT JOIN mit `users` Tabelle hinzufügen auf `processEvents.userId`
- User-Felder (name, email) zur SELECT-Klausel hinzufügen
- Return-Typ erweitern um User-Informationen

**Begründung für LEFT JOIN**:
- Einige Events könnten keine User-ID haben (System-Events, alte Einträge)
- Bei gelöschten Users würde INNER JOIN die Events ausblenden
- LEFT JOIN stellt sicher, dass alle Events angezeigt werden

**TypeScript-Änderungen**:
```typescript
// Return-Typ erweitern
Editor?: string[];  // Bleibt für Backwards-Kompatibilität
UserName?: string;   // NEU: Name des Users
UserEmail?: string;  // NEU: E-Mail des Users
```

### 2. TypeScript-Typen aktualisieren

**Datei**: `/src/lib/postgres-types.ts`  
**Interface**: `ContentLog`

**Änderungen**:
- `UserName?: string;` hinzufügen
- `UserEmail?: string;` hinzufügen
- Existierendes `Editor?: string[];` beibehalten für Kompatibilität

### 3. Frontend: History-Komponente erweitern

**Zu identifizierende Dateien**:
- Content-History Komponente (wahrscheinlich in `/src/components/` oder `/src/app/`)
- Table/List-Komponente die die Events anzeigt

**Änderungen**:
- Neue Spalte "Benutzer" oder "Ausgeführt von" hinzufügen
- User-Name anzeigen (falls vorhanden)
- Fallback zu "System" oder "Unbekannt" falls kein User zugeordnet

**Anzeigeformat-Optionen**:
1. **Nur Name**: "Max Mustermann"
2. **Name mit Email-Tooltip**: "Max Mustermann" (bei Hover: max@example.com)
3. **Name und Email**: "Max Mustermann (max@example.com)"
4. **Avatar + Name**: Avatar-Icon + "Max Mustermann"

### 4. Fehlende User-IDs ergänzen (Optional)

**Prüfen ob User-Tracking fehlt**:
Einige API-Routes könnten noch keine User-ID loggen. Nach der Implementierung sollte geprüft werden:

**Falls fehlend, Pattern verwenden**:
```typescript

const editor = session?.user?.id ? [session.user.id] : undefined;

await createContentLog({
  // ... andere Parameter

```

### 5. Migration für bestehende Daten (Optional)

**Überlegung**: 
- Alte Events haben möglicherweise keine User-IDs
- Diese werden mit LEFT JOIN als NULL angezeigt
- Keine Daten-Migration erforderlich, da kein Pflichtfeld

**Alternative**: 
- Für System-Events (z.B. automatische Vorschläge) könnte man einen speziellen System-User erstellen
- Dies ist aber optional und für den MVP nicht erforderlich

## Technische Details

### Relevante Code-Bereiche

**Database Schema** (`/src/lib/db/schema.ts`):
```typescript
process_events:
  - userId: text (FK zu users.id, ON DELETE SET NULL)
  
users:
  - id: text (PK, UUID)
  - name: text (nullable)
  - email: text (not null)
  - role: text
```

**Aktueller Event-Mapping** (`/src/lib/postgres.ts`, Zeilen 774-809):

## Entscheidungen zu klären

### Frage 1: Anzeigeformat
Wie sollen User in der Historie angezeigt werden?
- **Option A**: Nur Name (z.B. "Max Mustermann")
- **Option B**: Name + Email (z.B. "Max Mustermann (max@example.com)")
- **Option C**: Name mit Email-Tooltip (Hover zeigt Email)

**Empfehlung**: Option A mit Email-Tooltip (Option C), da es kompakt ist aber alle Infos verfügbar macht.

### Frage 2: Fallback für fehlende User
Was soll angezeigt werden wenn kein User zugeordnet ist?
- **Option A**: "System"
- **Option B**: "Unbekannt"
- **Option C**: Feld leer lassen

**Empfehlung**: "System" für automatische Events, macht die Herkunft klarer.

### Frage 3: Position in der Tabelle
Wo soll die User-Spalte erscheinen?
- **Option A**: Nach dem Event-Label (Event → User → Timestamp → Details)
- **Option B**: Vor dem Timestamp (Event → Details → User → Timestamp)
- **Option C**: Als erste Spalte (User → Event → Details → Timestamp)

**Empfehlung**: Option A - logischer Lesefluss "Was wurde gemacht → von wem → wann → Details".

## Risiken & Mitigationen

| Risiko | Wahrscheinlichkeit | Impact | Mitigation |
|--------|-------------------|---------|------------|
| Performance-Problem bei vielen Events | Niedrig | Mittel | LEFT JOIN ist effizient, Index auf user_id existiert bereits |
| Gelöschte User führen zu Fehlern | Niedrig | Hoch | LEFT JOIN + ON DELETE SET NULL verhindert dies |
| Alte Events ohne User-ID | Hoch | Niedrig | Fallback zu "System" implementieren |
| UI wird zu breit/unübersichtlich | Mittel | Niedrig | Responsive Design, optional Email-Tooltip statt inline |

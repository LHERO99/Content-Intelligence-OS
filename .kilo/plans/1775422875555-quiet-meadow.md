# Plan: Fix Content-Log Recording and Missing Exports

The application is experiencing two main issues:
1.  **Deployment Failure**: Missing exports (`getConfig`, `updateConfig`, `getBlacklist`, etc.) in `src/lib/airtable.ts`.
2.  **Functional Failure**: Content logs are no longer being recorded in Airtable.

## Analysis
The "Export doesn't exist" errors are caused by `src/lib/airtable.ts` lacking functions required by various API routes.
The failure to record content logs likely stems from Airtable rejecting writes to computed/lookup fields (like `Target_URL` or `Action_Type` if misconfigured) or silent validation errors.

### Key Findings:
- `createContentLog` currently attempts to write to fields without robust error handling or retries for computed fields (Airtable 422 error).
- URL handling is inconsistent; we need to use `Logged_URL` for persistent storage and handle `Target_URL` as a lookup.

## Proposed Changes

### 1. Robust `createContentLog` in `src/lib/airtable.ts`
Implement a more resilient `createContentLog` that handles the Airtable "computed field" error (422) by retrying without the problematic fields.
- Use `Logged_URL` for the URL value provided at creation.
- Add detailed logging for creation attempts.

### 2. Standardized Content-Log Retrieval
Update `getContentLogs`, `getContentHistoryByUrl`, etc., to resolve URLs correctly (handling arrays from lookups and falling back to `Logged_URL`).

### 3. Missing Exports in `src/lib/airtable.ts`
Re-add all necessary exports for configuration, blacklist, and trends that were previously identified as missing.

### 4. API Route Update (`src/app/api/planning/history/route.ts`)
Standardize the POST handler to ensure URLs are correctly mapped to `Logged_URL`.

## Verification Plan
1.  **Build Check**: Run `npm run build` to ensure all export issues are resolved.
2.  **Manual Test**: Trigger a content log via the UI/POST and verify it appears in Airtable.
3.  **Lint Check**: Run `npm run lint`.

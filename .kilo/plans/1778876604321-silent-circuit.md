# Plan: Fix — Delivery-Log-Isolation + Read-only bei Published

## Problem

Wenn ein Keyword zwei Zyklen hat (Erstellung → Optimierung) und der User im Optimierungszyklus Content anpasst, zeigt anschließend **auch die Erstellung** den neuen Inhalt.

### Root Cause

Der temporale Fallback in `buildJobEntries` (`src/app/creation/page.tsx:92–102`) sucht für jeden Beauftragungszyklus das **früheste** `"Content angeliefert"`-Log desselben Keywords nach dem Beauftragungsdatum. Für den **Erstellungszyklus** (Cycle A) gibt es kein `Commission_Log_Id` auf dem Delivery-Log (pre-migration Datensatz). Der Filter lautet:

```ts
dl.Commission_Log_Id == null &&
dl.Keyword_ID[0] === kwId &&
new Date(dl.Created_At).getTime() > new Date(commissionedAt).getTime()
```

Wenn der Optimierungszyklus (Cycle B) **nach der Migration** beauftragt wurde:
- Das Delivery-Log von Cycle B hat `Commission_Log_Id = B-ID` → wird korrekt per FK zugewiesen und **nicht** im Fallback verwendet.
- Das Delivery-Log von Cycle A hat `Commission_Log_Id = null` → landet im Fallback.
- **Cycle A bekommt korrekt seinen eigenen Delivery-Log** ✓

Wenn der Optimierungszyklus **vor der Migration** beauftragt wurde (beide Delivery-Logs haben `Commission_Log_Id = null`):
- Der Fallback ordnet Cycle A das früheste Delivery-Log nach Cycle-A-Datum zu — das ist das Delivery-Log von Cycle A ✓
- Cycle B (Optimierung, später) bekommt das früheste Delivery-Log nach Cycle-B-Datum — das könnte das Delivery-Log von Cycle B sein ✓

Das klingt korrekt. **Aber:** Nach dem manuellen Speichern im Editor erstellt `handleSaveContent` einen neuen Log mit `Event_Label: 'Manuelle Textanpassung im Editor'`. Dieser Log hat `Commission_Log_Id = B-ID` (korrekt) und `Version: 'v2'` — aber er ist **kein** Delivery-Log (kein `"Content angeliefert"`). Der `deliveryLogId` für Cycle B zeigt also weiterhin auf das originale Delivery-Log von Cycle B.

**Das eigentliche Symptom tritt auf, wenn der `bodyCache` veraltet ist:**

Die `bodyCache`-Logik in `page.tsx` lädt den Body eines Logs **einmalig** und speichert ihn unter der `deliveryLogId`. Wenn der User:
1. Cycle B (Optimierung) auswählt → `deliveryLogId = X` → Body von X wird gecacht
2. Im Editor Content ändert und speichert → `workingContent` aktualisiert sich lokal
3. Polling-Refresh passiert → `contentLogs` aktualisiert sich
4. `buildJobEntries` läuft neu → `deliveryLogId` für Cycle B bleibt `X` (delivery ist immer noch das originale "Content angeliefert"-Log)
5. Cycle A (Erstellung) auswählt → `deliveryLogId` für Cycle A → Body von Cycle-A-Delivery-Log wird angezeigt ✓

Noch kein Problem sichtbar. **Aber:** Wenn der User nach dem Speichern **im Workspace bleibt** und dann Cycle A auswählt, ändert sich `deliveryLogId` auf Cycle-A-ID. Falls der Cache diesen noch nicht hat, lädt er ihn.

Das Problem tritt auf, wenn:

### Tatsächlicher Bug: `deliveryLogId` nach dem Speichern nicht aktualisiert

Nach `handleSaveContent` → `window.dispatchEvent('refresh-planning-data')` → `fetchData()` lädt neue `contentLogs`. `buildJobEntries` läuft neu. Die Frage ist: ändert sich `deliveryLogId` für Cycle B nach dem Speichern?

**Ja, das kann passieren:** Der neu gespeicherte Log mit `Event_Label: 'Manuelle Textanpassung'` hat `Version: 'v2'`. Wenn der `deliveryLogs`-Filter in Zukunft geändert oder anders interpretiert wird, könnte dieser Log als Delivery erkannt werden. **Aber** der aktuelle Filter ist `l.Event_Label === 'Content angeliefert'` — das schließt manuelle Anpassungen aus.

### Eigentlicher zweiter Bug: `bodyCache` wird nicht invalidiert

Wenn der User Content in Cycle B speichert → neuer Log entsteht → `deliveryLogId` für Cycle B bleibt **unverändert** auf dem alten Delivery-Log → `bodyCache[deliveryLogId]` ist bereits gesetzt → wird **nicht neu geladen** (Guard: `if (bodyCache[deliveryLogId] !== undefined) return`).

Das bedeutet: der Editor zeigt nach dem Speichern den neuen `workingContent` (lokaler State), aber nach einem **Page-Reload** oder nach dem **Wegklicken und zurückkommen** zeigt er wieder den alten angelieferten Inhalt — nicht den zuletzt gespeicherten.

### Eigentlicher dritter Bug (wahrscheinlichster Grund für das gemeldete Symptom)

Nach dem Speichern im Optimierungszyklus dispatcht der Editor `refresh-planning-data`. Dadurch wird `contentLogs` neu geladen. Der neue Log "Manuelle Textanpassung" hat `Version: 'v2'` und `Commission_Log_Id = B-ID`. **In `buildJobEntries` ändert sich `deliveryLogId` für Cycle B nicht** (delivery bleibt "Content angeliefert"-Log). Aber:

**Der `bodyCache` key für `deliveryLogId` von Cycle B ist schon befüllt.** Wenn der User jedoch Cycle A auswählt, lädt er den Body von Cycle-A's `deliveryLogId`. Falls `deliveryLogId` für Cycle A und Cycle B **identisch** sind (weil der Fallback denselben Log zugewiesen hat), zeigen beide dasselbe.

Das passiert wenn: die Erstellung hat **kein eigenes** "Content angeliefert"-Log (weil z.B. die Erstellung vor der Implementierung der Delivery-Logs stattfand oder der Delivery-Log nicht erstellt wurde). Dann findet der Fallback für Cycle A gar kein Delivery-Log → `deliveryLogId = undefined`. Ohne `deliveryLogId` zeigt die Page den Spinner. Das ist nicht das Symptom.

**Wahrscheinlichster Grund:** Die `deliveryLogs` für Cycle B nach dem manuellen Speichern — der manuelle Speichern erzeugt einen neuen `Version: 'v2'`-Log. `buildJobEntries` filtert nur auf `l.Event_Label === 'Content angeliefert'` für deliveryLogs. **Aber** wenn der Filter fehlt oder ein Versehen vorliegt, könnte der neue manuelle Log als delivery für Cycle A erkannt werden.

**Klareres Bild nach nochmaliger Analyse:**

Der manuelle Speichervorgang erstellt einen neuen Log mit:
- `Event_Label: 'Manuelle Textanpassung im Editor'`
- `Commission_Log_Id: B-ID`
- `Version: 'v2'` (weil `contentBody` vorhanden)

`buildJobEntries` definiert `deliveryLogs` als:
```ts
contentLogs.filter(l => l.Event_Label === 'Content angeliefert' && l.Version === 'v2')
```

Der neue manuelle Log hat `Event_Label !== 'Content angeliefert'` → er ist **nicht** in `deliveryLogs` → wird **nicht** als delivery zugewiesen. ✓

**Der `bodyCache`-Bug ist aber real:** Nach dem Speichern bleibt `deliveryLogId` auf dem originalen Delivery-Log (z.B. ID 50). Der Editor zeigt den neuen Content nur, weil `workingContent` lokal gesetzt wurde. Nach einem Hard-Reload oder nach dem Neu-Laden der Seite würde `bodyCache[50]` immer noch den alten angelieferten Inhalt zeigen, nicht den zuletzt gespeicherten.

**Kernproblem:** `deliveryLogId` soll auf den **zuletzt gespeicherten v2-Content** zeigen, nicht auf den **erstmalig angelieferten Content**. Aktuell ist es auf `"Content angeliefert"` eingeschränkt. Nach einem manuellen Speichern gibt es aber einen neueren v2-Log, der den aktuellen Stand repräsentiert.

## Lösung

### Ansatz: `deliveryLogId` auf den neuesten v2-Log mit Content_Body zeigen lassen (zyklus-spezifisch)

**Statt:** den Delivery-Log (Erstanlieferung) als Quelle für den anzuzeigenden Content zu verwenden  
**Neu:** den **neuesten** v2-Log, der diesem Beauftragungszyklus gehört, als `displayLogId` verwenden

Das bedeutet:
1. `deliveryLogId` bleibt weiterhin das originale "Content angeliefert"-Log (für Status-Bestimmung)
2. Ein neues Feld `displayLogId` zeigt auf den neuesten Log mit `Commission_Log_Id === cl.ID` und `Version === 'v2'` (oder Fallback auf `deliveryLogId`)
3. Der Editor lädt den Body von `displayLogId`, nicht von `deliveryLogId`

### Änderungen

#### 1. `JobEntry`-Interface erweitern (`creation/page.tsx`)

```ts
interface JobEntry {
  commissionLogId: number;
  commissionedAt: string;
  keywordId: string;
  keyword: string;
  targetUrl?: string;
  actionType: 'Erstellung' | 'Optimierung';
  keywordStatus: KeywordStatus;
  deliveryLogId?: number;   // original "Content angeliefert" log (status-relevant)
  displayLogId?: number;    // neuester v2-Log für diesen Zyklus (content-relevant)
  isFailedRetry: boolean;
}
```

#### 2. `buildJobEntries` erweitern (`creation/page.tsx`)

Zusätzlich zu `deliveryLogs` eine neue Kategorie `latestContentLogs` ermitteln: alle v2-Logs mit `Commission_Log_Id !== null`, gruppiert nach `Commission_Log_Id`, jeweils der neueste:

```ts
// Neuester v2-Log per commission cycle (für Anzeige im Editor)
const latestV2LogByCommission = new Map<number, ContentLog>();
for (const log of contentLogs) {
  if (log.Version !== 'v2' || log.Commission_Log_Id == null) continue;
  const existing = latestV2LogByCommission.get(log.Commission_Log_Id);
  if (!existing || new Date(log.Created_At) > new Date(existing.Created_At)) {
    latestV2LogByCommission.set(log.Commission_Log_Id, log);
  }
}
```

Dann in der `commissioningLogs.map`:
```ts
const latestV2Log = latestV2LogByCommission.get(cl.ID);
const displayLogId = latestV2Log?.ID ?? delivery?.ID;
```

#### 3. `creation/page.tsx` — `displayLogId` statt `deliveryLogId` für den Body-Load

```ts
// Body on-demand loading: immer den neuesten v2-Content des Zyklus laden
const displayLogId = selectedJob?.displayLogId
  ? String(selectedJob.displayLogId)
  : null;

useEffect(() => {
  if (!displayLogId || bodyCache[displayLogId] !== undefined) return;
  fetch(`/api/planning/history/${displayLogId}/body`)
    ...
}, [displayLogId]);

const v2Content = displayLogId ? bodyCache[displayLogId]?.Content_Body ?? '' : '';
```

#### 4. `bodyCache`-Invalidierung nach dem Speichern

Nach einem erfolgreichen Speichern im Editor sendet `window.dispatchEvent('refresh-planning-data')`. Die Page lädt neue `contentLogs`. Weil `buildJobEntries` den neuesten v2-Log als `displayLogId` zurückgibt, ändert sich `displayLogId` für den aktiven Zyklus auf die neue Log-ID. Der `useEffect` erkennt, dass der Cache für die neue ID noch leer ist, und lädt den frischen Body.

**Kein explizites Cache-Invalidieren nötig** — das neue `displayLogId` sorgt automatisch für einen Reload.

#### 5. Fallback für Zyklen ohne `Commission_Log_Id` (pre-migration)

Wenn `latestV2LogByCommission` für einen Zyklus keinen Eintrag hat (weil alle Logs `Commission_Log_Id = null` haben), fällt `displayLogId` auf `deliveryLogId` zurück — identisches Verhalten wie bisher.

## Wichtig: Pre-migration Fallback

Für Zyklen ohne `Commission_Log_Id` auf irgendwelchen Logs bleibt `displayLogId = deliveryLogId` (Fallback). Das stellt sicher, dass bestehende Daten weiterhin korrekt angezeigt werden.

## Feature: Read-only-Modus wenn Zyklus "Veröffentlicht"

### Anforderung

Sobald ein Zyklus als "Veröffentlicht" markiert wurde (`keywordStatus === 'Published'`), sollen weder der Editor noch der KI-Chat-Tab mehr bearbeitbar sein. Nur die Vorschau bleibt zugänglich.

### Analyse

`AIEditorWorkspace` bekommt `currentStatus: KeywordStatus` als Prop. Dieser Wert kommt aus `selectedKeyword?.Status` in `page.tsx`.

Das Problem: `currentStatus` ist der globale Keyword-Status. Bei mehreren Zyklen zeigt er für ältere Zyklen nicht den zyklus-spezifischen Status — das wurde mit `keywordStatus` im `JobEntry` gelöst, aber dieser Wert wird momentan **nicht** an `AIEditorWorkspace` übergeben. `page.tsx` übergibt `currentStatus={selectedKeyword?.Status ?? 'Beauftragt'}` — immer den globalen Keyword-Status.

Nach der `commission_log_id`-Migration ist aber `selectedJob.keywordStatus` der korrekte per-Zyklus-Status. Dieser ist `'Published'` für veröffentlichte Zyklen, unabhängig vom globalen `kw.Status`.

### Lösung

**Schritt 1 — `page.tsx`: `currentStatus` mit dem zyklus-spezifischen Status befüllen**

```tsx
currentStatus={selectedJob.keywordStatus}
```

statt:

```tsx
currentStatus={selectedKeyword?.Status ?? 'Beauftragt'}
```

Das ist korrekt, weil `selectedJob.keywordStatus` bereits die per-Zyklus-Logik aus `buildJobEntries` enthält.

**Schritt 2 — `ai-editor-workspace.tsx`: Bearbeiten und KI-Chat bei Published sperren**

Ein `isReadOnly`-Flag ableiten:

```ts
const isReadOnly = currentStatus === 'Published';
```

Dann:

- **"Bearbeiten"-Tab**: `disabled` wenn `isReadOnly` — Button ausgegraut, kein `onClick`
- **"KI-Optimierung"-Tab**: `disabled` wenn `isReadOnly` — Button ausgegraut, kein `onClick`  
- **Publish-Button**: bereits disabled wenn nicht `'Angeliefert'` — bleibt unverändert
- **Toolbar-Hinweis**: kleiner Text oder Tooltip "Veröffentlichter Content kann nicht mehr bearbeitet werden" wenn `isReadOnly`

Wenn der User bereits im Edit- oder AI-Chat-Modus ist und der Status sich auf Published ändert (durch Polling), wird `activeMode` auf `'preview'` zurückgesetzt:

```ts
useEffect(() => {
  if (isReadOnly) setActiveMode('preview');
}, [isReadOnly]);
```

| Datei | Änderung |

| `src/app/creation/page.tsx` | `currentStatus` Prop auf `selectedJob.keywordStatus` ändern |
| `src/app/creation/ai-editor-workspace.tsx` | `isReadOnly` Flag; Tabs deaktivieren; useEffect für Forced-Preview |

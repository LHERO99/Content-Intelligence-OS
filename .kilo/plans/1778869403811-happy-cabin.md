# Plan: System-Zustand und DB-Migrationen prüfen

Dieses Dokument beschreibt die nächsten Schritte zur Validierung des System-Zustands und zur Durchführung ausstehender Datenbank-Migrationen, basierend auf dem aktuellen Stand der `docs/memory/` Dokumentation.

## Aktueller Status
Das System zeigt ein fehlerhaftes Verhalten beim Workflow von der Vorschlagsliste bis zur Content-Anlieferung, insbesondere bei Optimierungen. Der aktuelle Prozess überspringt teilweise Schritte oder führt zu inkonsistenten Zuständen in der Auftrags-Historie.

## Gewünschter Workflow
1.  **Vorschlag:** Thema erscheint im Tab "Vorschläge" (Typ: "Erstellung" oder "Optimierung").
2.  **Planung:** Durch Klick auf "Hinzufügen" wandert das Thema in den Tab "Redaktionsplan" (Status: `Planned`). Der Typ ("Erstellung" oder "Optimierung") wird dabei explizit übernommen.
3.  **Beauftragung:** Durch Klick auf "Beauftragen" im Redaktionsplan wird der Prozess gestartet (Status: `Beauftragt`). Das Thema verschwindet aus dem Redaktionsplan.
4.  **Content-Erstellung:** Das Thema erscheint in der Liste "Content-Erstellung" mit dem korrekten Typ.
5.  **Anlieferung:** Nach Anlieferung (Status: `Angeliefert`) und Veröffentlichung (Status: `Published`) kann das Thema später erneut zur Optimierung vorgeschlagen werden.
6.  **Re-Zirkulation:** Ein optimiertes Thema muss denselben Workflow durchlaufen (Vorschläge -> Redaktionsplan -> Beauftragen -> Anlieferung) und dabei einen **neuen** Log-Eintrag in der Historie erzeugen, statt den alten zu überschreiben.

## Fehlerursachen
1.  **Typ-Verlust in der Planung:** Der "Hinzufügen"-Button im Vorschläge-Tab übernimmt den `Action_Type` nicht immer korrekt bzw. die API setzt ihn teilweise hart zurück.
2.  **Harter Status-Sprung:** Der Agent-Trigger setzt den Status sofort auf `Beauftragt`, was die Unterscheidung zwischen "in Planung" und "wirklich beauftragt" erschwert, wenn die UI nicht synchron ist.
3.  **Anzeige-Logik in der Content-Erstellung:** Die Liste in der Content-Erstellung filtert teilweise unsauber und greift für den Typ ("Erstellung"/"Optimierung") auf Log-Einträge zu, die bei parallelen oder aufeinanderfolgenden Aufträgen zu Verwirrung führen können.
4.  **Historien-Überschreibung:** Wenn ein Thema erneut beauftragt wird, wird oft der `Action_Type` auf dem Keyword-Record geändert, was die Sicht auf vergangene Aktionen verfälscht, wenn die Log-Einträge nicht sauber getrennt sind.

## Ziele
1.  **Saubere Typ-Mitführung:** Der `Action_Type` ("Erstellung"/"Optimierung") wird vom Vorschlag über die Planung bis zur Beauftragung strikt beibehalten.
2.  **Workflow-Integrität:** Einträge verschwinden erst bei echtem Status-Wechsel (`Beauftragt`) aus dem Redaktionsplan.
3.  **Eindeutige Auftrags-Liste:** In der "Content-Erstellung" wird pro Beauftragung ein klarer Zustand angezeigt, basierend auf dem aktuellsten Log-Eintrag dieses Typs.

## Geplante Schritte

### 1. API-Anpassungen (Keywords & Trigger)
*   **`src/app/api/planning/keywords/route.ts` (PATCH)**: Sicherstellen, dass `Action_Type` niemals implizit geändert wird, außer es wird explizit im Payload mitgeschickt. Die automatische Rücksetzung auf "Erstellung" bei `Status: 'Planned'` wird entfernt.
*   **`src/app/api/agent-webhook/trigger/route.ts`**: Den `Action_Type` für das Logging und den Workflow-Payload strikt aus dem Request-Body oder dem aktuellen Datenbank-Zustand ableiten.

### 2. UI-Anpassungen (Redaktionsplan & Vorschläge)
*   **`src/features/planning/components/suggestion-columns.tsx`**: Der "Hinzufügen"-Button übergibt den `Action_Type` des Vorschlags explizit an die API.
*   **`src/app/planning/editorial-planning.tsx`**: Die `handleCommissionContent`-Funktion muss den `Action_Type` des Keywords an den `triggerN8nAction`-Aufruf übergeben, damit der Agent weiß, ob er erstellen oder optimieren soll.

### 3. Content-Erstellung Liste (UI-Fix)
*   **`src/app/creation/page.tsx`**: Die Anzeige des Typs ("Erstellung" oder "Optimierung") in der Liste links wird so angepasst, dass sie den `Action_Type` der **aktuellen Beauftragung** (aus dem Status oder dem neuesten Log) anzeigt, statt hart auf den ersten Log-Eintrag zu schauen.

### 4. Datenmodell & Logging
*   Verifizierung, dass `createContentLog` bei jeder Beauftragung einen neuen Eintrag erzeugt. Das ist technisch bereits so, aber die UI muss lernen, diese Einträge als separate "Events" in der Historie zu behandeln (was sie durch die `id` bereits tut).

## Validierung
1.  **Szenario Ersterstellung:** Hinzufügen -> Beauftragen -> Erscheint als "Erstellung" in Liste? -> OK.
2.  **Szenario Optimierung:** (Nach Veröffentlichung) -> Optimierung vorschlagen -> Erscheint in Vorschläge? -> Hinzufügen -> Erscheint im Redaktionsplan als "Optimierung"? -> Beauftragen -> Erscheint als "Optimierung" in Liste? -> OK.
3.  **Historie-Check:** Zeigt die Detail-Ansicht beide Aktionen (Erstellung UND Optimierung) separat an? -> OK.

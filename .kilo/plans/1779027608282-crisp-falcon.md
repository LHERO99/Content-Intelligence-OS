# Datenbankschema-Refactoring: Trennung von Status-Entitäten für Content-Prozesse

## Zusammenfassung

Dieses Dokument analysiert das aktuelle Datenbankschema für Content-Erstellung und Keyword-Mapping, identifiziert fundamentale Designprobleme durch die Vermischung von Prozess-Status auf URL/Keyword-Ebene und entwickelt ein überarbeitetes Schema mit separaten Status-Entitäten für jede Prozessphase.

---

## 1. Analyse des aktuellen Datenbankschemas

### 1.1 Zentrale Tabellen

#### **keyword_map**
Haupttabelle für URL-Keyword-Zuordnungen mit folgenden Schlüsselfeldern:

```typescript
{
  id: text PRIMARY KEY,
  tenantId: text NOT NULL,
  keyword: text NOT NULL,
  targetUrl: text NOT NULL,
  status: 'Backlog' | 'Planned' | 'Beauftragt' | 'In Arbeit' | 
          'Angeliefert' | 'Review' | 'Optimierung' | 'Published',
  actionType: 'Erstellung' | 'Optimierung',
  editorialDeadline: date,
  mainKeyword: 'Y' | 'N',
  searchVolume: integer,
  difficulty: integer,
  priorityScore: numeric,
  // ... weitere SEO-Metriken
}
```

**UNIQUE INDEX:** `(keyword, targetUrl, tenantId)`

**Bedeutung:** Eine URL kann mehrere Keywords haben, jedes Keyword-URL-Paar ist eindeutig.

#### **content_log** + **content_log_body**
Audit-Trail aller Content-Aktivitäten mit Zwei-Tabellen-Architektur:

```typescript
// content_log - Metadata
{
  id: serial PRIMARY KEY,
  tenantId: text NOT NULL,
  keywordId: text (FK → keyword_map),
  loggedUrl: text,
  actionType: 'Planung' | 'Erstellung' | 'Optimierung' | 'KI-Chat',
  pageType: 'Ratgeber' | 'Kategorie' | 'Marke' | 'Produkt',
  editorId: text (FK → users),
  timeCreated: timestamp,
  timeChanged: timestamp,
  commissionLogId: integer (self-reference)
}

// content_log_body - Large content storage
{
  contentLogId: integer PRIMARY KEY (FK → content_log),
  contentBody: text,
  eventLabel: text
}
```

### 1.2 Aktuelle Workflow-Architektur

```
KEYWORD_MAP.STATUS als zentrale State-Machine:

Backlog 
  ↓ [User: "Hinzufügen" in Suggestions]
Planned 
  ↓ [User: "Beauftragen" in Editorial Planning]
Beauftragt 
  ↓ [Agent: Start Processing]
In Arbeit 
  ↓ [Agent: Deliver Content via Webhook]
Angeliefert 
  ↓ [User: Review & Publish]
Published

Alternativ-Pfade:
- Beauftragt/In Arbeit → Planned (bei Fehler)
- Review (selten genutzt)
- Optimierung (Status vs. Action_Type Verwirrung)
```

**Logging-Events:**
- Jeder Status-Übergang erzeugt einen `content_log` Eintrag
- `commission_log_id` verknüpft Delivery/Save/Publish mit Commissioning
- `event_label` beschreibt die Aktion ("Content wurde beauftragt", etc.)

## 2. Identifizierte Probleme

### 2.1 Problem 1: Datenredundanz durch URL-zentrierte vs. Keyword-zentrierte Status

**Aktuelles Verhalten:**
- Eine URL kann 5-10 Keywords haben (ein Main-Keyword + mehrere Neben-Keywords)
- Jedes Keyword hat einen eigenen Status in `keyword_map`
- Status-Änderungen sind keyword-spezifisch, aber der Content-Erstellungsprozess ist **URL-zentriert**

**Konkrete Probleme:**

```
Beispiel: URL /best-laptops-2024

Keywords in keyword_map:
1. "beste laptops" (Main_Keyword: Y, Status: Beauftragt)
2. "laptop test" (Main_Keyword: N, Status: Backlog)
3. "laptop vergleich" (Main_Keyword: N, Status: Backlog)
4. "gaming laptop" (Main_Keyword: N, Status: Backlog)

Problem: Nur das Main-Keyword wird beauftragt, aber:
- Der Agent erstellt Content für die GESAMTE URL
- Alle Keywords profitieren vom selben Content
- Status der anderen Keywords bleibt auf "Backlog"
- Keine konsistente Repräsentation des URL-Status
```

**Redundanz-Szenarien:**

1. **Mehrfach-Beauftragung möglich:** Ohne Validation kann jedes Keyword separat beauftragt werden → mehrere Commissioning-Logs für dieselbe URL
2. **Inkonsistente Filtered Views:** Editorial Planning zeigt nur `Status: Planned` Keywords → nach Beauftragung verschwindet Keyword, aber andere Keywords derselben URL bleiben sichtbar
3. **Verlorene Status-Information:** Wenn ein Keyword gelöscht wird, geht dessen Status-Historie verloren (auch wenn die URL weiterhin existiert)

**Code-Beleg:**

`src/app/planning/editorial-planning.tsx:76`
```typescript
return keywords.filter(k => k.Status === 'Planned');
```
→ Zeigt nur `Planned` Keywords, nicht den URL-Gesamtstatus

`src/app/creation/page.tsx:162`
```typescript
isFailedRetry: isActiveCycle && keywordStatus === 'Planned' && !delivery
```
→ Erkennt Fehler nur durch Keyword-Status, nicht durch URL-Status

### 2.2 Problem 2: Fehlende Prozess-Trennung

**Vermischung von drei unabhängigen Prozessen in einem Status-Feld:**

| Prozess | Verantwortlichkeit | Aktueller Status |
|---------|-------------------|------------------|
| **Planung** | Redakteur | Backlog → Planned |
| **Umsetzung** | Agent/System | Beauftragt → In Arbeit → Angeliefert |
| **Veröffentlichung** | Redakteur/Publisher | Review → Published |

**Probleme:**

1. **Keine parallelen Workflows:** Ein Keyword kann nicht gleichzeitig "geplant" und "in Umsetzung" sein (z.B. Re-Commissioning während Review)
2. **Unklare Ownership:** Wer ist für Status-Übergänge verantwortlich? 
   - `Beauftragt` → `In Arbeit`: Implizit, kein Code gefunden
   - `Review`: Wird nie gesetzt, existiert nur in Type Definition
3. **Status-Übersprünge möglich:** Keine State-Machine-Validierung verhindert `Backlog` → `Published`

**Code-Beleg:**

`src/app/api/agent-webhook/trigger/route.ts:40-42`
```typescript
await updateKeyword(data.keywordId, { 
  Status: "Beauftragt",
  Action_Type: commissioningActionType 
}, tenantId);
```
→ Direkter Update ohne Validierung des vorherigen Status

`src/app/creation/ai-editor-workspace.tsx:215`
```typescript
disabled={isSaving || isPublished || currentStatus !== 'Angeliefert'}
```
→ Hard-coded Abhängigkeit: Publish nur wenn Status exakt `Angeliefert`

### 2.3 Problem 3: Konsistenzprobleme bei mehreren Einträgen pro URL

**Szenario: Multiple Commission Cycles**

```
Zyklus 1 (Erstellung):
- keyword_map.Status: Published
- content_log: Commission ID 123 → Delivery → Published

Zyklus 2 (Optimierung):
- keyword_map.Status: Beauftragt (überschreibt "Published"!)
- content_log: Commission ID 456 → ...
```

**Problem:** Der Status-Wechsel zu `Beauftragt` löscht die Information über die vorherige Veröffentlichung

**Aktuelle Kompensation:**
- `Last_Published` Datum in `keyword_map` (wird nicht aktualisiert bei Re-Commissioning)
- Multi-Cycle-Logik in `src/app/creation/page.tsx:123-144` rekonstruiert Status aus `content_log` und `commission_log_id`

**Code-Beleg:**

`src/app/creation/page.tsx:136-144`
```typescript
// Determine per-cycle status
if (isActiveCycle) {
  cycleStatus = keywordStatus;
} else {
  const publishLogForThisCycle = publishLogs.find(
    (pl) => pl.Commission_Log_Id === cl.ID
  );
  cycleStatus = publishLogForThisCycle ? 'Published' : 'Angeliefert';
}
```
→ Status-Rekonstruktion aus Logs, weil `keyword_map.Status` nicht pro Zyklus funktioniert

### 2.4 Problem 4: Content_Log als Workaround für fehlende State-Tables

**Aktuelle Nutzung:**
- `content_log` dient als Event-Sourcing-System
- Status-Übergänge werden durch `event_label` impliziert
- `commission_log_id` verknüpft zusammengehörige Events
- UI-Logik rekonstruiert Prozess-Status durch Log-Parsing

**Probleme:**

1. **Langsame Queries:** Filtern nach Status erfordert volltextuelle Log-Suche statt Index-Lookup
2. **Keine referentielle Integrität:** `event_label` ist Freitext → keine DB-Constraints
3. **Komplexe Aggregation:** `GROUP BY` und String-Matching für Status-Counts
4. **Migration-Alptraum:** Logik-Änderungen erfordern Reprocessing aller historischen Logs

**Code-Beleg:**

`src/app/api/agent-webhook/callback/route.ts:110-118`
```typescript
const isOptimization = status === 'Optimierung' || 
                      status === 'Optimization' ||
                      (body.diffSummary && body.diffSummary.toLowerCase().includes('optimiert')) ||
                      (body.actionType && body.actionType === 'Optimierung');
```
→ Heuristische Erkennung von Optimierungs-Workflows durch String-Matching

### 2.5 Problem 5: Action_Type vs. Status Konfusion

**Zwei überlappende Klassifikationen:**

| Feld | Werte | Zweck |
|------|-------|-------|
| `keyword_map.action_type` | Erstellung, Optimierung | Klassifiziert Workflow-Typ |
| `keyword_map.status` | Backlog, ..., Optimierung, Published | Prozess-Status UND manchmal Typ |

**Probleme:**

1. **"Optimierung" als Status:** Existiert in Type, wird aber selten genutzt → verwirrt mit `action_type: Optimierung`
2. **Semantische Überlappung:** "Optimierung beauftragt" könnte sein:
   - `status: Beauftragt` + `action_type: Optimierung`
   - oder `status: Optimierung` + `action_type: ?`
3. **Content_Log Action_Type hat 4 Werte:** `Planung | Erstellung | Optimierung | KI-Chat` → weitere Inkonsistenz

**Code-Beleg:**

`src/lib/postgres-types.ts:8-16`
```typescript
export type KeywordMapStatus = 
  'Backlog' | 'Planned' | 'Beauftragt' | 'In Arbeit' | 
  'Angeliefert' | 'Review' | 'Optimierung' | 'Published';
```

`src/lib/postgres-types.ts:18-19`
```typescript
export type ActionType = 'Erstellung' | 'Optimierung';
```
→ `Optimierung` existiert in beiden Enums

## 3. Auswirkungen auf die saubere Handhabung von Prozessen

### 3.1 Planungs-Prozess

**Aktuelle Probleme:**

1. **Keine URL-Aggregation:** Suggestions-Tab und Editorial Planning zeigen Keywords, nicht URLs
   - Redakteur muss mental gruppieren: "Ah, diese 5 Keywords gehören zur selben URL"
   - Drag & Drop von Keywords einzeln statt ganzer URLs

2. **Deadline-Management kompliziert:** `editorial_deadline` ist pro Keyword, aber Redakteur plant pro URL
   - Was wenn Main-Keyword Deadline 01.05. hat, Neben-Keyword 15.05.?
   - Welche Deadline gilt für den Agent?

3. **Priority-Score-Fragmentierung:** Jedes Keyword hat eigenen Score
   - URL-Priorität = max(keyword scores)? avg()? Unklar.

**Code-Beleg:**

`src/app/planning/suggestions-table.tsx:78-88`
```typescript
return keywords.filter(kw =>
  kw.Main_Keyword === 'Y' &&
  !activeWorkflowStatuses.has(kw.Status ?? '') &&
  (kw.Status === 'Backlog' || !!optimizationSuggestions[kw.id] || kw.Action_Type === 'Optimierung')
);
```
→ Filter auf Keyword-Ebene, keine URL-Aggregation

### 3.2 Umsetzungs-Prozess

**Aktuelle Probleme:**

1. **Agent-Webhook-Kopplung zu Keywords:** 
   - Webhook erwartet `keywordId`, aber Agent arbeitet URL-basiert
   - Was wenn Agent Content für alle Keywords liefert, aber nur ein `keywordId` im Callback?

2. **Fehlende Versionierung:** Multiple Deliveries überschreiben sich
   - Zyklus-Tracking über `commission_log_id` ist Workaround
   - Kein explizites "Version 1 Published, Version 2 in Review"-Konzept

3. **Retry-Logik fragil:**
   ```typescript
   await updateKeyword(keywordId, { Status: 'Planned' }, tenantId);
   ```
   → Reset zu `Planned` löscht Information über `Beauftragt`-Datum, Editor, etc.

**Code-Beleg:**

`src/app/api/agent-webhook/callback/route.ts:126`
```typescript
await updateKeyword(keywordId, { Status: 'Angeliefert' }, tenantId);
```
→ Status-Update auf Keyword-Ebene, obwohl Content URL-bezogen ist

### 3.3 Veröffentlichungs-Prozess

**Aktuelle Probleme:**

1. **Hard-coded Status-Validierung:**
   ```typescript
   disabled={currentStatus !== 'Angeliefert'}
   ```
   → Publish-Button nur aktiviert wenn exakt `Angeliefert`
   → Was wenn Status manuell auf `Review` gesetzt wurde?

2. **Kein Approval-Workflow:** Direct Path `Angeliefert` → `Published`
   - Keine Trennung Review vs. Publish
   - Keine Mehrstufige Freigabe (z.B. Editor → Senior Editor → Publisher)

3. **Last_Published als Datums-Feld:** Keine Information über:
   - Wer hat veröffentlicht?
   - Welche Version wurde veröffentlicht?
   - War es Partial-Publish oder Full-Publish?

**Code-Beleg:**

`src/app/api/planning/keywords/route.ts:291-300`
```typescript
await updateKeyword(recordId, {
  Status: 'Published',
  Last_Published: new Date().toISOString().split('T')[0]
}, tenantId);
```
→ Einfaches Datums-Update, keine strukturierte Publishing-Entity

## 4. Überarbeitetes Datenbankschema

### 4.1 Design-Prinzipien

1. **URL-First:** URLs sind primäre Einheiten, Keywords sind Attribute
2. **Prozess-Separation:** Jeder Prozess (Planning, Execution, Publishing) hat eigene Status-Tabellen
3. **Immutable Events:** Status-Änderungen sind Events, keine Updates
4. **Explicit State Machines:** Validierung von Status-Übergängen auf DB-Ebene
5. **Multi-Cycle Native:** Versionierung und Cycle-Tracking als First-Class-Konzept

### 4.2 Kern-Schema

#### **urls** (Neue Haupttabelle)

```sql
CREATE TABLE urls (
  id TEXT PRIMARY KEY DEFAULT gen_random_uuid()::text,
  tenant_id TEXT NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
  url TEXT NOT NULL,
  page_type TEXT, -- 'Ratgeber' | 'Kategorie' | 'Marke' | 'Produkt'
  created_at TIMESTAMP WITH TIME ZONE DEFAULT now() NOT NULL,
  updated_at TIMESTAMP WITH TIME ZONE DEFAULT now() NOT NULL,
  
  CONSTRAINT urls_url_tenant_unique UNIQUE(url, tenant_id)
);

CREATE INDEX urls_tenant_idx ON urls(tenant_id);
CREATE INDEX urls_page_type_idx ON urls(tenant_id, page_type);
```

**Rationale:**
- URLs sind atomare Einheiten des Content-Managements
- Trennung von URL-Metadaten (page_type, created_at) von Keyword-Daten
- Basis für URL-zentrierte Prozess-Entities

#### **url_keywords** (Refactored keyword_map)

```sql
CREATE TABLE url_keywords (
  id TEXT PRIMARY KEY DEFAULT gen_random_uuid()::text,
  tenant_id TEXT NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
  url_id TEXT NOT NULL REFERENCES urls(id) ON DELETE CASCADE,
  keyword TEXT NOT NULL,
  is_main_keyword BOOLEAN DEFAULT false NOT NULL,
  search_volume INTEGER,
  difficulty INTEGER,
  ranking INTEGER,
  priority_score NUMERIC,
  -- SEO-Metriken bleiben hier
  article_count INTEGER,
  avg_product_value NUMERIC,
  policy NUMERIC,
  created_at TIMESTAMP WITH TIME ZONE DEFAULT now() NOT NULL,
  
  CONSTRAINT url_keywords_keyword_url_tenant_unique UNIQUE(keyword, url_id, tenant_id)
);

CREATE INDEX url_keywords_tenant_idx ON url_keywords(tenant_id);
CREATE INDEX url_keywords_url_idx ON url_keywords(url_id);
CREATE INDEX url_keywords_main_kw_idx ON url_keywords(tenant_id, url_id, is_main_keyword);
CREATE INDEX url_keywords_priority_idx ON url_keywords(tenant_id, priority_score DESC);
```

**Rationale:**
- Fokus auf SEO-Metriken und Keyword-Attribute
- **KEIN Status-Feld** → Status lebt in separaten Tabellen
- `is_main_keyword` als Boolean (klarer als 'Y'/'N')
- Beziehung über `url_id` statt redundantem `target_url` Text

#### **keyword_rankings** (Refactored keyword_ranking_history)

```sql
CREATE TABLE keyword_rankings (
  id SERIAL PRIMARY KEY,
  tenant_id TEXT NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
  keyword_id TEXT NOT NULL REFERENCES url_keywords(id) ON DELETE CASCADE,
  date DATE NOT NULL,
  ranking INTEGER,
  
  CONSTRAINT keyword_rankings_kw_date_tenant_unique UNIQUE(keyword_id, date, tenant_id)
);

CREATE INDEX keyword_rankings_tenant_idx ON keyword_rankings(tenant_id);
CREATE INDEX keyword_rankings_date_idx ON keyword_rankings(tenant_id, date DESC);
CREATE INDEX keyword_rankings_kw_date_idx ON keyword_rankings(tenant_id, keyword_id, date DESC);
```

**Rationale:**
- Unverändert, nur `keyword_id` zeigt auf `url_keywords`

### 4.3 Prozess-Status-Tabellen

#### **planning_status** (Planungs-Prozess)

```sql
CREATE TYPE planning_status_enum AS ENUM (
  'suggested',      -- System hat URL vorgeschlagen
  'backlog',        -- User sieht URL, noch nicht geplant
  'planned',        -- URL ist im Editorial Calendar
  'cancelled'       -- Planung wurde abgebrochen
);

CREATE TABLE planning_status (
  id SERIAL PRIMARY KEY,
  tenant_id TEXT NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
  url_id TEXT NOT NULL REFERENCES urls(id) ON DELETE CASCADE,
  status planning_status_enum NOT NULL DEFAULT 'backlog',
  editorial_deadline DATE,
  priority_score NUMERIC,
  planned_action_type TEXT, -- 'creation' | 'optimization'
  assigned_editor_id TEXT REFERENCES users(id) ON DELETE SET NULL,
  created_at TIMESTAMP WITH TIME ZONE DEFAULT now() NOT NULL,
  updated_at TIMESTAMP WITH TIME ZONE DEFAULT now() NOT NULL,
  
  CONSTRAINT planning_status_url_tenant_unique UNIQUE(url_id, tenant_id)
);

CREATE INDEX planning_status_tenant_idx ON planning_status(tenant_id);
CREATE INDEX planning_status_status_idx ON planning_status(tenant_id, status);
CREATE INDEX planning_status_deadline_idx ON planning_status(tenant_id, editorial_deadline);
CREATE INDEX planning_status_editor_idx ON planning_status(assigned_editor_id);
```

**Rationale:**
- **URL-basiert:** Eine URL hat genau einen Planning Status
- **Separater Lifecycle:** Unabhängig von Execution/Publishing
- `editorial_deadline` und `assigned_editor` gehören zur Planung
- `priority_score` hier, weil es Planungs-Relevanz hat

**State-Machine:**
```
suggested → backlog → planned → cancelled
         ↓         ↓        ↓
      (auto)   (manual)  (ready for execution)
```

#### **execution_cycles** (Umsetzungs-Prozess)

```sql
CREATE TYPE execution_status_enum AS ENUM (
  'commissioned',   -- Auftrag erteilt
  'in_progress',    -- Agent arbeitet
  'delivered',      -- Agent hat geliefert
  'failed',         -- Fehlgeschlagen
  'cancelled'       -- Abgebrochen
);

CREATE TABLE execution_cycles (
  id SERIAL PRIMARY KEY,
  tenant_id TEXT NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
  url_id TEXT NOT NULL REFERENCES urls(id) ON DELETE CASCADE,
  cycle_number INTEGER NOT NULL, -- 1, 2, 3... für Re-Commissioning
  action_type TEXT NOT NULL, -- 'creation' | 'optimization'
  status execution_status_enum NOT NULL DEFAULT 'commissioned',
  commissioned_by_user_id TEXT REFERENCES users(id) ON DELETE SET NULL,
  commissioned_at TIMESTAMP WITH TIME ZONE DEFAULT now() NOT NULL,
  delivered_at TIMESTAMP WITH TIME ZONE,
  failed_at TIMESTAMP WITH TIME ZONE,
  failure_reason TEXT,
  agent_run_id TEXT, -- External agent system reference
  created_at TIMESTAMP WITH TIME ZONE DEFAULT now() NOT NULL,
  updated_at TIMESTAMP WITH TIME ZONE DEFAULT now() NOT NULL,
  
  CONSTRAINT execution_cycles_url_cycle_tenant_unique UNIQUE(url_id, cycle_number, tenant_id)
);

CREATE INDEX execution_cycles_tenant_idx ON execution_cycles(tenant_id);
CREATE INDEX execution_cycles_url_idx ON execution_cycles(url_id);
CREATE INDEX execution_cycles_status_idx ON execution_cycles(tenant_id, status);
CREATE INDEX execution_cycles_commissioned_at_idx ON execution_cycles(commissioned_at DESC);
```

**Rationale:**
- **Cycle-First:** Multi-Cycle-Support als natives Konzept
- **Immutable Commissioning:** Neuer Cycle = neue Row
- **Explicit Lifecycle:** commissioned → in_progress → delivered/failed
- Timestamps für jede Phase (SLA-Tracking möglich)

**State-Machine:**
```
commissioned → in_progress → delivered
           ↓              ↓
       cancelled       failed
```

**Query-Beispiel:**
```sql
-- Active cycle per URL
SELECT DISTINCT ON (url_id) *
FROM execution_cycles
WHERE tenant_id = $1 AND status IN ('commissioned', 'in_progress')
ORDER BY url_id, cycle_number DESC;
```

#### **execution_versions** (Content-Versionen)

```sql
CREATE TABLE execution_versions (
  id SERIAL PRIMARY KEY,
  tenant_id TEXT NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
  cycle_id INTEGER NOT NULL REFERENCES execution_cycles(id) ON DELETE CASCADE,
  version_number INTEGER NOT NULL, -- 1 = initial delivery, 2+ = manual edits
  content_html TEXT,
  diff_summary TEXT,
  created_by_user_id TEXT REFERENCES users(id) ON DELETE SET NULL,
  created_by_ai BOOLEAN DEFAULT false,
  ai_provider TEXT,
  ai_model TEXT,
  ai_instructions TEXT,
  created_at TIMESTAMP WITH TIME ZONE DEFAULT now() NOT NULL,
  
  CONSTRAINT execution_versions_cycle_version_unique UNIQUE(cycle_id, version_number)
);

CREATE INDEX execution_versions_cycle_idx ON execution_versions(cycle_id);
CREATE INDEX execution_versions_created_at_idx ON execution_versions(created_at DESC);
```

**Rationale:**
- Ersetzt `content_log_body` mit strukturierter Versionierung
- Jede Änderung (Agent-Delivery, Manual Edit, AI-Chat) = neue Version
- Trennung von Versionsdaten und Metadaten
- `version_number` auto-incrementiert pro Cycle

**Beziehung:**
```
execution_cycles 1 ─────── N execution_versions
       ↓
     Status: delivered = cycle.id hat ≥1 version
```

#### **publishing_status** (Veröffentlichungs-Prozess)

```sql
CREATE TYPE publishing_status_enum AS ENUM (
  'draft',          -- Initiale Version, unpublished
  'in_review',      -- Zur Review eingereicht
  'approved',       -- Review abgeschlossen, bereit zum Publish
  'published',      -- Live auf der Website
  'unpublished'     -- Wurde veröffentlicht, dann zurückgezogen
);

CREATE TABLE publishing_status (
  id SERIAL PRIMARY KEY,
  tenant_id TEXT NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
  cycle_id INTEGER NOT NULL REFERENCES execution_cycles(id) ON DELETE CASCADE,
  version_id INTEGER NOT NULL REFERENCES execution_versions(id) ON DELETE CASCADE,
  status publishing_status_enum NOT NULL DEFAULT 'draft',
  reviewed_by_user_id TEXT REFERENCES users(id) ON DELETE SET NULL,
  reviewed_at TIMESTAMP WITH TIME ZONE,
  review_notes TEXT,
  published_by_user_id TEXT REFERENCES users(id) ON DELETE SET NULL,
  published_at TIMESTAMP WITH TIME ZONE,
  unpublished_by_user_id TEXT REFERENCES users(id) ON DELETE SET NULL,
  unpublished_at TIMESTAMP WITH TIME ZONE,
  unpublish_reason TEXT,
  created_at TIMESTAMP WITH TIME ZONE DEFAULT now() NOT NULL,
  updated_at TIMESTAMP WITH TIME ZONE DEFAULT now() NOT NULL,
  
  CONSTRAINT publishing_status_cycle_unique UNIQUE(cycle_id, tenant_id)
);

CREATE INDEX publishing_status_tenant_idx ON publishing_status(tenant_id);
CREATE INDEX publishing_status_status_idx ON publishing_status(tenant_id, status);
CREATE INDEX publishing_status_published_at_idx ON publishing_status(published_at DESC);
```

**Rationale:**
- **Pro Cycle:** Jeder Execution-Cycle kann separat publiziert werden
- **Review-Workflow:** Explizite Trennung Draft → Review → Approved → Published
- **Audit-Trail:** Wer hat wann reviewt/publiziert?
- **Rollback-Support:** Unpublish mit Reason-Tracking

**State-Machine:**
```
draft → in_review → approved → published → unpublished
     ↓           ↓          ↓
  (direct)   (rejected)  (direct)
```

**Query-Beispiel:**
```sql
-- Aktuell publizierte Version pro URL
SELECT 
  u.url,
  ec.cycle_number,
  ev.version_number,
  ps.published_at
FROM urls u
JOIN execution_cycles ec ON ec.url_id = u.id
JOIN execution_versions ev ON ev.cycle_id = ec.id
JOIN publishing_status ps ON ps.cycle_id = ec.id
WHERE u.tenant_id = $1
  AND ps.status = 'published'
ORDER BY u.url, ec.cycle_number DESC, ev.version_number DESC;
```

### 4.4 Audit-Trail (Refactored content_log)

#### **process_events** (Ersatz für content_log)

```sql
CREATE TYPE event_type_enum AS ENUM (
  -- Planning Events
  'url_suggested',
  'url_added_to_backlog',
  'url_planned',
  'planning_cancelled',
  
  -- Execution Events
  'cycle_commissioned',
  'cycle_started',

);

CREATE TABLE process_events (
  id SERIAL PRIMARY KEY,
  tenant_id TEXT NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
  event_type event_type_enum NOT NULL,
  
  -- Polymorphic references
  url_id TEXT REFERENCES urls(id) ON DELETE SET NULL,
  keyword_id TEXT REFERENCES url_keywords(id) ON DELETE SET NULL,
  planning_status_id INTEGER REFERENCES planning_status(id) ON DELETE SET NULL,
  cycle_id INTEGER REFERENCES execution_cycles(id) ON DELETE SET NULL,
  version_id INTEGER REFERENCES execution_versions(id) ON DELETE SET NULL,

);

CREATE INDEX process_events_tenant_idx ON process_events(tenant_id);
CREATE INDEX process_events_url_idx ON process_events(url_id);

CREATE INDEX process_events_type_idx ON process_events(event_type);
CREATE INDEX process_events_timestamp_idx ON process_events(tenant_id, event_timestamp DESC);
```

**Rationale:**

- **Strukturierte References:** FK zu allen relevanten Entities statt Freitext-URLs

## 5. Vorteile des neuen Schemas

### 5.1 Modularisierung von Prozessen

**Vorher:**
```
keyword_map.status: 8 Werte, 3 Prozesse vermischt
→ Eine State-Machine für alles
```

**Nachher:**
```
planning_status: 4 Werte (suggested → backlog → planned → cancelled)
execution_cycles: 5 Werte (commissioned → in_progress → delivered/failed/cancelled)
publishing_status: 5 Werte (draft → in_review → approved → published → unpublished)

→ Drei unabhängige State-Machines
```

**Ermöglicht:**
1. **Parallele Workflows:** URL kann `planned` sein während vorheriger Cycle `in_review` ist
2. **Klare Ownership:** Planning = Redakteur, Execution = System, Publishing = Publisher/Redakteur
3. **Feinere Zugriffsrechte:** User-Rolle "Reviewer" kann nur `publishing_status` ändern

### 5.2 Vereinfachte Status-Logik

**Vorher (keyword_map):**
```typescript
// 15 verschiedene Stellen prüfen Status
if (keyword.Status === 'Angeliefert') { ... }

// Rekonstruktion aus Logs
const cycleStatus = publishLogs.find(...) ? 'Published' : 'Angeliefert';

// Inkonsistente Filter
const activeWorkflowStatuses = new Set(['Planned', 'Beauftragt', ...]);
```

**Nachher:**
```typescript
// Direkte Queries
const activeCycles = await db
  .select()
  .from(executionCycles)
  .where(and(
    eq(executionCycles.tenantId, tenantId),
    inArray(executionCycles.status, ['commissioned', 'in_progress'])
  ));

// Kein Log-Parsing nötig
const publishedVersion = await db
  .select()
  .from(publishingStatus)
  .where(and(
    eq(publishingStatus.cycleId, cycleId),
    eq(publishingStatus.status, 'published')
  ))
  .limit(1);
```

**Vorteile:**
- **Index-optimiert:** Status-Filter nutzen B-Tree-Indizes statt Volltextsuche
- **Typsicherheit:** Enums statt String-Literals
- **Keine Heuristiken:** Direkter Zugriff auf Status, kein String-Matching

### 5.3 Datenintegrität

**Constraints:**

1. **State-Machine-Validierung (via Trigger):**
```sql
CREATE FUNCTION validate_execution_status_transition() RETURNS TRIGGER AS $$
BEGIN
  IF OLD.status = 'delivered' AND NEW.status = 'commissioned' THEN
    RAISE EXCEPTION 'Cannot transition from delivered to commissioned';
  END IF;
  -- ... weitere Rules
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER execution_status_guard
  BEFORE UPDATE ON execution_cycles
  FOR EACH ROW EXECUTE FUNCTION validate_execution_status_transition();
```

2. **Referentielle Integrität:**
- `publishing_status.version_id` FK → nur existierende Versionen publizierbar
- `execution_versions.cycle_id` FK → Versionen gehören zu validen Cycles
- CASCADE-Deletes: URL löschen → alle Statuses/Cycles werden mitgelöscht

3. **Unique Constraints:**
- `(url_id, cycle_number)` → keine duplizierten Cycles
- `(cycle_id, version_number)` → konsistente Versionierung

### 5.4 URL-zentrierte Architektur

**Zentrale URL-Entity:**
```sql
urls
  ├── url_keywords (1:N)
  ├── planning_status (1:1)
  ├── execution_cycles (1:N)
  │     ├── execution_versions (1:N)
  │     └── publishing_status (1:1)
  └── url_performance (1:N historical)
```

**Query-Pattern:**
```sql
-- Vollständiger URL-Status mit einem JOIN
SELECT 
  u.url,
  u.page_type,
  ps.status AS planning_status,
  ps.editorial_deadline,
  ec.status AS execution_status,
  ec.cycle_number,
  pb.status AS publishing_status,
  pb.published_at
FROM urls u
LEFT JOIN planning_status ps ON ps.url_id = u.id
LEFT JOIN execution_cycles ec ON ec.url_id = u.id AND ec.cycle_number = (
  SELECT MAX(cycle_number) FROM execution_cycles WHERE url_id = u.id
)
LEFT JOIN publishing_status pb ON pb.cycle_id = ec.id
WHERE u.tenant_id = $1;
```

**Vorteile:**
- **Single Source of Truth:** URL-ID als primärer Schlüssel
- **Aggregierte Views:** Keywords als Attribute, nicht als primäre Entities
- **Performance:** Join-optimiert statt Log-Parsing

### 5.5 Native Multi-Cycle-Support

**Cycle-Lifecycle:**
```
Cycle 1 (Creation):
  execution_cycles.id = 100, cycle_number = 1, action_type = 'creation'
  → execution_versions.id = 200, version_number = 1 (initial delivery)
  → execution_versions.id = 201, version_number = 2 (manual edit)
  → publishing_status.id = 300, status = 'published', version_id = 201

Cycle 2 (Optimization):
  execution_cycles.id = 101, cycle_number = 2, action_type = 'optimization'
  → execution_versions.id = 202, version_number = 1 (re-delivery)
  → publishing_status.id = 301, status = 'in_review', version_id = 202
```

**Queries:**
```sql
-- Alle Cycles einer URL
SELECT * FROM execution_cycles WHERE url_id = $1 ORDER BY cycle_number;

-- Aktuell published Version
SELECT ev.*
FROM execution_cycles ec
JOIN publishing_status ps ON ps.cycle_id = ec.id
JOIN execution_versions ev ON ev.id = ps.version_id
WHERE ec.url_id = $1 AND ps.status = 'published'
ORDER BY ec.cycle_number DESC LIMIT 1;

-- In-Progress Cycle (exklusiv)
SELECT * FROM execution_cycles
WHERE url_id = $1 AND status IN ('commissioned', 'in_progress')
LIMIT 1;
```

**Vorteil:** Kein `commission_log_id`-Workaround, native DB-Struktur

```sql
-- 0007_backfill_urls_from_keyword_map.sql

-- 1. URLs aus keyword_map extrahieren
INSERT INTO urls (id, tenant_id, url, page_type, created_at)
SELECT 
  gen_random_uuid()::text,
  tenant_id,
  target_url,
  page_type,
  MIN(created_at) -- Falls keyword_map.created_at existiert
FROM keyword_map
GROUP BY tenant_id, target_url, page_type
ON CONFLICT (url, tenant_id) DO NOTHING;

-- 2. Keywords migrieren
INSERT INTO url_keywords (id, tenant_id, url_id, keyword, is_main_keyword, ...)
SELECT 
  km.id,
  km.tenant_id,
  u.id AS url_id,
  km.keyword,
  (km.main_keyword = 'Y'),
  km.search_volume,
  km.difficulty,
  -- ...
FROM keyword_map km
JOIN urls u ON u.url = km.target_url AND u.tenant_id = km.tenant_id;

-- 3. Planning Status ableiten
INSERT INTO planning_status (tenant_id, url_id, status, editorial_deadline, ...)
SELECT DISTINCT ON (u.id)
  u.tenant_id,
  u.id,
  CASE 
    WHEN km.status IN ('Backlog') THEN 'backlog'::planning_status_enum
    WHEN km.status IN ('Planned') THEN 'planned'::planning_status_enum
    ELSE 'backlog'::planning_status_enum
  END,
  km.editorial_deadline,
  -- ...
FROM urls u
JOIN keyword_map km ON km.target_url = u.url AND km.tenant_id = u.tenant_id
WHERE km.main_keyword = 'Y' -- Nur Main-Keyword bestimmt Planning-Status
ORDER BY u.id, km.priority_score DESC NULLS LAST;

-- 4. Execution Cycles aus content_log rekonstruieren
WITH commissioning_logs AS (
  SELECT 
    cl.id,
    cl.tenant_id,
    cl.keyword_id,
    km.target_url,
    cl.action_type,
    cl.time_created,
    cl.editor_id,
    ROW_NUMBER() OVER (
      PARTITION BY km.target_url, km.tenant_id 
      ORDER BY cl.time_created
    ) AS cycle_number
  FROM content_log cl
  JOIN keyword_map km ON km.id = cl.keyword_id
  WHERE cl.event_label ILIKE '%beauftragt%' 
    OR cl.action_type IN ('Erstellung', 'Optimierung')
)
INSERT INTO execution_cycles (
  id, tenant_id, url_id, cycle_number, action_type, 
  status, commissioned_at, commissioned_by_user_id
)
SELECT 
  c.id,
  c.tenant_id,
  u.id,
  c.cycle_number,
  CASE c.action_type
    WHEN 'Erstellung' THEN 'creation'
    WHEN 'Optimierung' THEN 'optimization'
  END,
  CASE 
    WHEN EXISTS (
      SELECT 1 FROM content_log cl2 
      WHERE cl2.commission_log_id = c.id 
        AND cl2.event_label ILIKE '%angeliefert%'
    ) THEN 'delivered'::execution_status_enum
    ELSE 'failed'::execution_status_enum
  END,
  c.time_created,
  c.editor_id
FROM commissioning_logs c
JOIN urls u ON u.url = c.target_url AND u.tenant_id = c.tenant_id;

-- 5. Execution Versions aus content_log_body
WITH delivery_and_saves AS (
  SELECT 
    cl.id,
    cl.commission_log_id AS cycle_id,
    cl.tenant_id,
    clb.content_body,
    clb.event_label,
    cl.editor_id,
    cl.time_created,
    ROW_NUMBER() OVER (
      PARTITION BY cl.commission_log_id 
      ORDER BY cl.time_created
    ) AS version_number
  FROM content_log cl
  JOIN content_log_body clb ON clb.content_log_id = cl.id
  WHERE cl.commission_log_id IS NOT NULL
    AND clb.content_body IS NOT NULL
)
INSERT INTO execution_versions (
  tenant_id, cycle_id, version_number, content_html,
  diff_summary, created_by_user_id, created_at
)
SELECT 
  d.tenant_id,
  d.cycle_id,
  d.version_number,
  d.content_body,
  d.event_label,
  d.editor_id,
  d.time_created
FROM delivery_and_saves d;

-- 6. Publishing Status ableiten
INSERT INTO publishing_status (
  tenant_id, cycle_id, version_id, status, 
  published_at, published_by_user_id
)
SELECT 
  ec.tenant_id,
  ec.id,
  ev.id,
  CASE 
    WHEN km.status = 'Published' THEN 'published'::publishing_status_enum
    WHEN km.status = 'Review' THEN 'in_review'::publishing_status_enum
    WHEN km.status = 'Angeliefert' THEN 'approved'::publishing_status_enum
    ELSE 'draft'::publishing_status_enum
  END,
  km.last_published,
  cl.editor_id
FROM execution_cycles ec
JOIN urls u ON u.id = ec.url_id
JOIN keyword_map km ON km.target_url = u.url AND km.tenant_id = u.tenant_id
LEFT JOIN execution_versions ev ON ev.cycle_id = ec.id AND ev.version_number = (
  SELECT MAX(version_number) FROM execution_versions WHERE cycle_id = ec.id
)
LEFT JOIN content_log cl ON cl.commission_log_id = ec.id 
  AND cl.event_label ILIKE '%veröffentlicht%'
WHERE km.main_keyword = 'Y';

-- 7. Process Events aus content_log
INSERT INTO process_events (
  tenant_id, event_type, url_id, cycle_id, 
  user_id, event_data, event_timestamp
)
SELECT 
  cl.tenant_id,
  CASE 
    WHEN cl.event_label ILIKE '%beauftragt%' THEN 'cycle_commissioned'::event_type_enum
    WHEN cl.event_label ILIKE '%angeliefert%' THEN 'cycle_delivered'::event_type_enum
    WHEN cl.event_label ILIKE '%veröffentlicht%' THEN 'content_published'::event_type_enum
    WHEN cl.action_type = 'Planung' THEN 'url_planned'::event_type_enum
    ELSE 'version_created'::event_type_enum
  END,
  u.id,
  cl.commission_log_id,
  cl.editor_id,
  jsonb_build_object(
    'original_event_label', clb.event_label,
    'action_type', cl.action_type,
    'page_type', cl.page_type
  ),
  cl.time_created
FROM content_log cl
LEFT JOIN content_log_body clb ON clb.content_log_id = cl.id
LEFT JOIN keyword_map km ON km.id = cl.keyword_id
LEFT JOIN urls u ON u.url = COALESCE(cl.logged_url, km.target_url) 
  AND u.tenant_id = cl.tenant_id;
```

### 7.2 Materialized Views

**Problem:** Aggregierte Dashboard-Queries sind teuer

**Lösung:** Materialized Views mit automatischem Refresh

```sql
-- Aggregierte URL-Status für Dashboard
CREATE MATERIALIZED VIEW url_status_dashboard AS
SELECT 
  u.id AS url_id,
  u.url,
  u.tenant_id,
  ps.status AS planning_status,
  ps.editorial_deadline,
  ps.assigned_editor_id,
  ec.id AS active_cycle_id,
  ec.cycle_number AS active_cycle,
  ec.status AS execution_status,
  ec.commissioned_at,
  pub.status AS publishing_status,
  pub.published_at,
  (
    SELECT COUNT(*) 
    FROM url_keywords 
    WHERE url_id = u.id
  ) AS keyword_count,
  (
    SELECT COUNT(*) 
    FROM execution_versions 
    WHERE cycle_id = ec.id
  ) AS version_count
FROM urls u
LEFT JOIN planning_status ps ON ps.url_id = u.id
LEFT JOIN LATERAL (
  SELECT * FROM execution_cycles 
  WHERE url_id = u.id 
  ORDER BY cycle_number DESC 
  LIMIT 1
) ec ON true
LEFT JOIN publishing_status pub ON pub.cycle_id = ec.id;

CREATE UNIQUE INDEX url_status_dashboard_pkey ON url_status_dashboard(url_id);
CREATE INDEX url_status_dashboard_tenant_idx ON url_status_dashboard(tenant_id);

-- Automatischer Refresh (Trigger oder Cron-Job)
CREATE FUNCTION refresh_url_status_dashboard() RETURNS void AS $$
BEGIN
  REFRESH MATERIALIZED VIEW CONCURRENTLY url_status_dashboard;
END;
$$ LANGUAGE plpgsql;

-- Trigger on relevant tables (optional)

AFTER INSERT OR UPDATE OR DELETE ON planning_status
```

```typescript
export async function getCachedDashboard(tenantId: string) {
  const cacheKey = `dashboard:${tenantId}`;
  let data = dashboardCache.get(cacheKey);
  
  if (!data) {
    data = await db.select().from(urlStatusDashboard)
      .where(eq(urlStatusDashboard.tenantId, tenantId));
    dashboardCache.set(cacheKey, data);
  }
  
  return data;
}
```

### 8.2 Skalierbarkeit

**Anforderung:** Unterstützung für 100k+ URLs, Millionen Events

**Maßnahmen:**

1. **Normalisierung:** URLs als eigene Entities → keine redundanten Text-Kopien
2. **Indizierung:** Alle FK + Status-Felder indiziert

### 8.3 Fehlervermeidung

**Anforderung:** Dateninkonsistenzen verhindern, Fehler früh erkennen

**Maßnahmen:**

1. **DB-Level Constraints:**
```sql
-- Zyklus kann nicht in_progress sein wenn bereits delivered
CREATE FUNCTION prevent_status_regression() RETURNS TRIGGER AS $$
BEGIN
  IF OLD.status = 'delivered' AND NEW.status = 'in_progress' THEN
    RAISE EXCEPTION 'Cannot regress from delivered to in_progress';
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER execution_status_validation
BEFORE UPDATE ON execution_cycles
FOR EACH ROW EXECUTE FUNCTION prevent_status_regression();
```

2. **Foreign Key Constraints:**
- `publishing_status.version_id` → nur existierende Versionen publizierbar
- `ON DELETE CASCADE` → keine orphaned Status-Rows

3. **Type-Safety:**
```typescript
// Generated from DB schema
type PlanningStatus = 'suggested' | 'backlog' | 'planned' | 'cancelled';
type ExecutionStatus = 'commissioned' | 'in_progress' | 'delivered' | 'failed' | 'cancelled';

// Compiler verhindert typos
await updatePlanningStatus(urlId, 'planed'); // ❌ Compile error
await updatePlanningStatus(urlId, 'planned'); // ✅
```

4. **Transactional Consistency:**
```typescript
async function commissionCycle(urlId: string, userId: string) {
  return db.transaction(async (tx) => {
    // 1. Create cycle
    const [cycle] = await tx.insert(executionCycles).values({
      urlId,
      cycleNumber: await getNextCycleNumber(urlId, tx),
      actionType: 'creation',
      status: 'commissioned',
      commissionedByUserId: userId,
    }).returning();
    
    // 2. Log event
    await tx.insert(processEvents).values({
      eventType: 'cycle_commissioned',
      urlId,
      cycleId: cycle.id,
      userId,
    });
    
    // 3. Update planning status (optional)
    await tx.update(planningStatus)
      .set({ updatedAt: new Date() })
      .where(eq(planningStatus.urlId, urlId));
    
    return cycle;
  });
}
```

**Fehlerfälle automatisch abgefangen:**
- Publishing ohne Delivery → FK constraint violation
- Doppelte Cycle-Numbers → Unique constraint violation
- Inkonsistente Status-Übergänge → Trigger prevents

## 9. Risiken & Mitigationen

### 9.1 Migration-Risiken

| Risiko | Wahrscheinlichkeit | Impact | Mitigation |
|--------|-------------------|--------|------------|
| **Datenverlust bei Backfill** | Niedrig | Hoch | - Backup vor Migration<br>- Dual-Write-Phase (neue + alte Tabellen)<br>- Rollback-Plan |
| **Performance-Degradation** | Mittel | Mittel | - Staging-Tests mit Production-Snapshot<br>- Schrittweise Rollout<br>- Query-Performance-Monitoring |
| **Inkonsistenzen alte ↔ neue Daten** | Mittel | Mittel | - Validierungs-Queries nach jedem Schritt<br>- Automated Consistency Checks<br>- Reconciliation-Jobs |
| **Code-Bugs nach Umstellung** | Hoch | Mittel | - Feature-Flags für graduelle Umstellung<br>- Umfassende Tests<br>- Tenant-by-Tenant Rollout |

**Rollback-Plan:**
```sql

```

### 9.2 Komplexitäts-Risiken

**Problem:** Mehr Tabellen = komplexere Queries?

**Gegenargument:**
- Aktuelle Komplexität ist versteckt (Log-Parsing, Status-Rekonstruktion)
- Neue Queries sind explizit und typsicher
- JOINs sind performanter als Substring-Matching

**Beispiel:**
```sql
-- ALT: Implizite Komplexität
SELECT * FROM content_log 
WHERE event_label ILIKE '%angeliefert%' 
  AND commission_log_id IN (
    SELECT id FROM content_log WHERE event_label ILIKE '%beauftragt%'
  );

-- NEU: Explizite Relationen
SELECT * FROM execution_cycles
WHERE status = 'delivered';
```

### 9.3 Over-Engineering-Risiko

**Problem:** Zu viele Tabellen für aktuellen Use-Case?

**Argumentation:**
- Aktuelles System zeigt bereits Pain-Points (Multi-Cycle, Status-Konfusion)
- Neues Schema adressiert existierende Bugs, keine hypothetischen Features
- Modular: Nicht genutzte Tabellen (z.B. `legal_review_status`) können später hinzugefügt werden

**Minimale Implementierung (MVP):**
- Phase 1: Nur `urls`, `url_keywords`, `planning_status`

## 11. Zusammenfassung

### 11.1 Kern-Probleme des aktuellen Schemas

1. **Datenredundanz:** Status auf Keyword-Ebene, aber Prozesse sind URL-zentriert
2. **Fehlende Prozess-Trennung:** Ein Status-Feld für drei unabhängige Workflows
3. **Konsistenzprobleme:** Multi-Cycle-Support durch Workarounds statt native Struktur
4. **Content_Log-Missbrauch:** Event-Log als Ersatz für Status-Tabellen
5. **Action_Type/Status-Konfusion:** Semantische Überlappung

### 11.2 Lösungsansatz

**URL-First-Architektur:**
- URLs als primäre Entities, Keywords als Attribute
- Separate Status-Tabellen für Planning, Execution, Publishing
- Native Multi-Cycle-Support durch `execution_cycles` + `execution_versions`
- Strukturiertes Event-Sourcing mit `process_events`

**Vorteile:**
- ✅ Modularisierte Prozesse (klare Verantwortlichkeiten)
- ✅ Vereinfachte Status-Logik (Index-optimierte Queries)
- ✅ Datenintegrität (DB-Constraints, Transaktionen)
- ✅ Skalierbarkeit (Partitionierung, Materialized Views)
- ✅ Flexibilität (erweiterbare Enums, JSONB-Payloads)

**Migrations-Strategie:**
- Additive Migration ohne Downtime
- Schrittweises Backfilling historischer Daten
- Feature-Flag-basierte Code-Umstellung
- Tenant-by-Tenant Rollout

**Risiken & Mitigationen:**
- Backups + Rollback-Plan
- Extensive Validierung nach jedem Schritt
- Performance-Tests auf Staging
- Beta-Kunden als Pilot

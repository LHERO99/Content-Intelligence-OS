# Plan: Optimierung der Performance-Daten-Speicherung

Dieses Dokument beschreibt die Umstellung der Performance-Daten-Speicherung von einer kombinierten Tabelle auf zwei spezialisierte Tabellen in Airtable, um Redundanzen zu reduzieren und die Performance-Analyse zu verbessern.

## Fehlerkorrektur & Finalisierung der Migration

Der "Failed to fetch" Fehler in der Monitoring-Übersicht liegt daran, dass der API-Route `/api/monitoring` noch die Funktion `getPerformanceData()` aufruft, welche intern versucht, auf die nun gelöschte Tabelle `Performance_Data` zuzugreifen. Zudem werden URLs nicht angezeigt, weil die Liste der URLs aus dieser (leeren/fehlenden) Tabelle generiert wird.

### Schritte zur Fehlerbehebung:

1.  **Airtable Service (`airtable.ts`)**:
    *   `getPerformanceData()` so anpassen, dass sie Daten aus der neuen Tabelle `URL_Performance` liest.
    *   Hinzufügen einer Funktion `getAllURLPerformance()`, die alle Datensätze aus `URL_Performance` zurückgibt.
2.  **Monitoring API (`/api/monitoring/route.ts`)**:
    *   Umstellen der Datenquelle von `getPerformanceData()` auf die neue URL-basierte Logik.
    *   Anpassung der URL-Extraktion: Statt aus der redundanten Keyword-Tabelle werden die URLs nun direkt aus `URL_Performance` bezogen.
3.  **Bereinigung**:
    *   Vollständiges Entfernen von `TABLES.PERFORMANCE_DATA` aus dem Code, um zukünftige 403-Fehler zu vermeiden.

### Zeitplan:
- [ ] Refactoring `airtable.ts`: Umleitung von `getPerformanceData` auf `URL_Performance`.
- [ ] Refactoring `route.ts`: Anpassung der Metrik-Berechnung an die neue Tabellenstruktur.
- [ ] Verifikation: Test der Monitoring-Übersicht und der Detail-Charts.

# Plan: Fehlerbehebung und Optimierung des n8n Webhook-Calls

Der aktuelle Webhook-Call für `IMPORT_DATA` (GSC-History-Report) scheint nicht anzukommen, und das Anlegen von Keywords dauert zu lange. Dies liegt wahrscheinlich daran, dass der API-Call blockierend (mit `await`) ausgeführt wird und eventuell ein Problem mit der Request-Struktur (Payload/Header) vorliegt.

## Analyse
1.  **Blockierendes Warten:** In `src/app/api/planning/keywords/route.ts` wird auf `triggerN8nWorkflow` gewartet. Wenn n8n langsam antwortet oder ein Timeout läuft, verzögert das die gesamte API-Antwort für den Nutzer.
2.  **Request-Struktur:** Der Webhook wurde auf `POST` umgestellt. Wir müssen sicherstellen, dass n8n den Body korrekt empfängt und keine Header fehlen.
3.  **Fehlende Protokollierung:** Wir sehen aktuell nicht genau, was an n8n gesendet wird und was zurückkommt.

## Anpassung der Airtable Struktur und n8n-Rückgabe

### 1. Analyse der bestehenden Performance_Data Struktur
Die aktuelle Struktur (`src/lib/airtable-types.ts`) sieht wie folgt aus:
- `Target_URL`: String (Eindeutige Zuordnung zur Seite)
- `Date`: String (Datum der Messung)
- `GSC_Clicks`: Number
- `GSC_Impressions`: Number
- `Position`: Number (Average Position der URL)
- `Sistrix_VI`: Number
- `Source`: 'GSC' | 'Sistrix' | 'Combined'

### 2. Geplante Anpassung der Airtable-Tabelle `Performance_Data`
Um die wöchentlichen Daten und Keyword-Rankings valide zu erfassen, sind keine strukturellen Änderungen an den Feldern zwingend erforderlich, aber die **Datendichte** ändert sich:
- **Wöchentliche URL-Daten:** n8n sendet pro Woche einen Datensatz für die URL. Das Feld `Date` sollte immer auf den Montag der jeweiligen Woche gesetzt werden, um Konsistenz zu gewährleisten.
- **Keyword-Rankings:** Da das Tool aktuell Keyword-Rankings primär in der `Keyword-Map` speichert (`Ranking`-Feld), sollte n8n beim Import auch die `Keyword-Map` direkt aktualisieren.

### 3. Beispiel JSON für den HTTP POST Request (von n8n an das Tool)
Um die Daten effizient zu verarbeiten, sollte n8n einen Batch-Request an einen neuen (oder erweiterten) API-Endpunkt senden.

**Empfohlener Payload:**
```json
{
  "targetUrl": "https://www.docmorris.de/beispiel-seite",
  "performanceData": [
    {
      "date": "2024-03-25",
      "clicks": 150,
      "impressions": 4500,
      "position": 12.5,
      "source": "GSC"
    },
    {
      "date": "2024-04-01",
      "clicks": 180,
      "impressions": 5200,
      "position": 11.2,
      "source": "GSC"
    }
  ],
  "rankings": [
    {
      "keywordId": "recABC123",
      "rank": 5
    },
    {
      "keywordId": "recXYZ789",
      "rank": 14
    }
  ]
}
```

### 4. Implementierungsschritte im Tool
1. **Neuer API-Endpunkt `src/app/api/monitoring/import/route.ts`:**
   - Empfängt den obigen Payload.
   - **De-Duplizierung / Upsert-Logik:** 
     - Für jeden Performance-Datensatz wird geprüft, ob für dieselbe Kombination aus `Target_URL` und `Date` (Woche) bereits ein Eintrag existiert.
     - Wenn ja, wird dieser aktualisiert (`update`).
     - Wenn nein, wird ein neuer Eintrag erstellt (`create`).
   - Aktualisiert die `Keyword-Map` mit den neuesten Rankings.
2. **Erweiterung `src/lib/airtable.ts`:**
   - Hinzufügen einer Hilfsfunktion `upsertPerformanceData(data: PerformanceData[])`. Diese Funktion sucht nach bestehenden Records für URL+Datum, um Duplikate zu vermeiden.
   - Hinzufügen einer Hilfsfunktion `bulkUpdateKeywordRankings(rankings: {id: string, rank: number}[])`.
